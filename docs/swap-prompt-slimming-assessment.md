# 互换(swap)提示词瘦身评估报告

> 编写:图灵科技 · 2026-08-28 · 分支 `feature/dify-dsl-migration`
> 背景:客户业务/IT 反馈互换提示词过于冗长——大量规则写死、历史 bug 以补丁形式回填进提示词,损害泛化性。
> 本报告是全量评估:定位冗长根因、量化瘦身空间、给出三档瘦身清单与结构性改造方案。
> 字符数口径:`wc -m`;token 为估算值(字符 ÷1.6)。

---

## 一、执行摘要

`app/prompts/swap/` 共 13 个文件、**约 154K 字符 ≈ 96.5K tokens**。评估结论:

- **可压缩至约 65K 字符(整体 -55%~-60%)**,其中约 **4 成属"零风险删除"档**(死重/悬空规则/重复陈述),仅需 eval 回归即可落地;
- 三大病灶:**① 错例回填式规则堆积**(占比最高,正是客户抱怨的"把 bug 写进提示词")、**② 用 LLM 干确定性代码的活**(5 个节点的唯一任务是正则提取订单号)、**③ 同一规则重复陈述 2~4 遍**;
- 发现 **4 类此前未知的质量问题**:悬空规则(引用从未注入的变量)、提示词承诺了不存在的后处理脚本、自相矛盾的补丁并存、**硬编码客户产品名/员工名(触碰 P0 红线)**;
- 单次图片下单的提示词开销 ≈ **47K tokens**(image_ocr 4.6K + image_extract 42K),是延迟与成本的最大单点。

| 文件 | 字符 | ≈tokens | 健康度 | 预估压缩 |
|---|---:|---:|---|---|
| image_extract.md | 67,371 | 42,100 | 🔴 重灾区 | **-60%** |
| place_order.md | 37,039 | 23,100 | 🔴 补丁密集 | -45% |
| excel_extract.md | 14,904 | 9,300 | 🟠 | -55%(结构化后 -80%) |

| confirm.md(旧合并版快照,无代码加载) | 1,450 | 900 | ⚪ 死文件 | 归档 |

## 二、病灶解剖(按类别,跨文件)

### 病灶 1 · 错例回填式规则(客户抱怨的核心,估占全家 25%~30%)

针对单个历史错例写的针对性禁令,特征是高度具体、条件嵌套、与通用原则冲突:

| 证据 | 位置 | 说明 |
|---|---|---|
| "全部清仓干扰后缀结束标识" | place_order 核心护栏 0(L13-16) | 为一个错例写了 4 层嵌套条件 + 专属例外 + 专属自检(第 11 条),约 2.4K 字符 |
| "禁止把字母 I 误写成 🇮🇹" | place_order L19 | 单次 LLM 输出事故的回填 |
| "严禁因标的以 S 开头把 BUY 翻成 SELL" | place_order L203 | 单错例;OTC 首位 B/S 规则本身一句话可说清 |
| "done bc / done cv"小写简写特判 | place_order L202 | 单错例 |
| **"POV 15% 空格"修正传奇** | image_extract ≥10 处 | 原规则与修正补丁并存,**至今自相矛盾**:L48 说 `"POV 50%"✓`,L279/L2057 仍说 `✗`;带删除线和"【修正】"字样的修订史留在生产提示词里 |
| "A股不是标的代码" | image_extract 重复 ≈9 处 | 一个错例回填 9 遍 |
| "11125/1300/LKQ 右对齐"错例图 | image_ocr 3 处 + image_extract 2 处 | 同一张错例图讲了 5 遍 |
| 中文括号→英文括号转换 | excel_extract 3 处 ≈3.5K | 同一错例讲 3 遍 |
| "示例污染防护"三大段 | image_extract ≈14K | 为防模型抄示例里的代码,铺了 14K 防护文字;其中"禁止列表"把示例代码又抄一遍,**反而强化污染源** |

**正确归宿**:这类错例应转化为 `tests/fixtures/` 的 golden 用例(项目 TDD 红线本就要求先写复现测试),提示词只保留单条通用原则。

### 病灶 2 · 用 LLM 干确定性代码的活

- **5 个 LLM 节点做正则的活**:cancel_order / query_order / confirm_order / confirm_cancel / confirm_modify 的唯一任务是提取 `H-YYYYMMDD-XXXXXXXXXX` 订单号(confirm_order 多一个"提取全部+去重")。`app/nodes/route_rules.py` 的 `SWAP_ORDER_PATTERN` 一行正则即可,**零幻觉、零成本、零延迟**。5 个提示词(4.8K tokens)+5 次 LLM 调用可整体去除。
- **确定性变换塞给 LLM**:量词展开(1.5万股→15000)、时间补零(9:00→09:00)、千分位逗号归一、@提及过滤、机器人名过滤——各花几十行规则教 LLM,实际应为代码前/后处理(项目已有 `prewash.py`/`aggregate.py`/`quote_hints.py` 先例)。
- **表格模式判定是"用自然语言写代码"**:image_extract 的模式路由(首行信号计数/`|` 分割/字段名命中计数,≈7K)是纯机械规则,应下沉为确定性 Python 预分类,LLM 只做模式内字段抽取。
- **excel 更进一步**:交易对手/标的/数量/方向 4 列是结构化数据,逐行直拷不需要 LLM;只有"执行方式"一列需解析。提示词可从 14.9K 缩到 ≈3K。

### 病灶 3 · 重复陈述(估占 15%~20%)

- place_order:同一规则在 核心护栏 → 字段规则 → 11 条输出自检 → user 模板尾注 里说 2~4 遍(数量单位规则完整出现 3 遍);
- intent:"撤单≠确认撤单"重复 4 遍、"禁止用 quote_content 判意图"重复 5 遍;
- image_extract:21 个 few-shot 中至少 6 组互相冗余(同一规则点 3~4 个示例),示例区 34.9K 中 JSON 全字段展开占 70%。

### 病灶 4 · 死重与悬空(此前未知,零风险可删)

- **JSON 格式禁令死重**:代码用 `with_structured_output(SwapPlaceOrderParams)`,schema 由 function calling 强制——所有"纯 JSON 输出/禁止 ```json 标记/绝对禁止说明文字"段落(每个文件都有,共约 4K)无从违反,纯属死重;
- **悬空规则**(引用从未注入的变量):image_extract 的 `bot_name_list`/`shortname_list` 全部规则、excel_extract 的 `total`/`序号` 双重验证全套(≈3.9K)、image_ocr 的对手列表占位符(原样发给了 VL 模型)——`multimodal.py` 组装的 user 消息里根本没有这些变量;
- **承诺了不存在的下游**:image_extract 宣称"后处理脚本自动计算 placeOrderPovPercent 分摊",全仓 grep 确认**该脚本未迁移**——需决策补代码或删承诺。

### 病灶 5 · 硬编码业务数据(触碰项目 P0 红线)

- image_extract L545:产品名特征词表混入**具体客户产品名片段**("盛景""臻选"),另有"测试/增强/精选/套利/配置"业务命名枚举;
- L497-499:证券名称样式词典("股份/科技/集团/…"、"Group/Corp/Inc/…")——名称分类字典必然过期;
- 示例内含**真实测试账户与员工名**("11125测试短名(张天琪专用)"等),且"瑞科激光+300747.SZ"相邻出现,变相教了名称→代码映射,与自身"禁止映射"规则冲突。

### 泛化性障碍 TOP 清单(闭集词表——客户输入稍变即失配)

| 障碍 | 位置 | 失配场景 |
|---|---|---|
| 首行"≥3 类订单信号"硬门槛 | image_extract | 首行是寒暄前缀"帮忙下一单:"→信号=0→误入表格模式,整单崩坏 |
| hasFastExecutionIntent 26 词闭集 | place_order | 客户说"尽早成交"(不在闭集)→false |
| POV 触发三条件闭集 | image_extract | "参与率20%"→null |
| 产品名特征词闭集 | image_extract | 新产品"XX稳健FOF"→识别失败 |
| 表头别名闭集 | image_extract | 表头写"证券简码/股数"→整表跌入兜底模式,行为突变 |
| 方向枚举闭集 | excel_extract | "加仓"不在表→丢失 |
| 数量禁小数点 | image_extract | "3500.0"→不识别 |
| 限价标签 K 枚举(15 个) | place_order | 新口语"挂个价"→失配 |

**通用解法**:闭集改"语义类 + 少量锚例"(如"表达希望尽快成交的任何说法"),把精确校验交给下游代码/后端;这正是客户要的泛化性。

## 三、三档瘦身清单(汇总)

### 零风险删除(≈39K 字符,仅需 eval 回归)

1. 全部 JSON 格式禁令段(structured output 已强制)
2. 全部悬空规则(bot_name_list/shortname_list/序号/total/对手列表占位符)
3. image_extract 示例污染防护三大段 → 压为 3 行原则;"POV 空格"矛盾旧文本与修订史;L2120-2194 与前文逐字重复的检查清单
4. intent 的重复段(撤单对比 4 遍留 1 遍、数据源禁令 5 遍留 1 遍)
5. image_ocr 死变量段 + "逐字符自问自答"仪式文
6. confirm.md 死文件归档

### 低风险合并(≈32K 字符,eval + 抽样人工比对)

1. image_extract 21 示例 → 8 个,JSON 只保留差异字段
2. excel_extract 4 示例 → 2;括号补丁 3 遍 → 1 条"逐字符原样复制"
3. place_order 输出自检 11 条与正文去重(自检只留互斥/完整性两条硬校验)
4. intent 43 示例 → 15 个左右(按意图×典型形态覆盖)
5. image_ocr 右对齐规则收敛到一处;错误-正确对照各留正确版

### 需业务确认(≈15K 字符 + 结构决策)

1. 删硬编码产品词/名称词典/示例真实账户名(P0 红线,建议必删,但需业务确认替代判定方式)
2. "A股非标的"等 9 处收敛为 1 条
3. image_extract 无字段名值块的"冲突展开/回退"全套(≈8K)——**该输入形态是否真有线上流量?** 无流量可整体降级
4. POV 分摊承诺:补后处理代码 or 删承诺(需拍板)
5. "全部清仓结束标识"护栏 0:确认原始业务诉求后改写为 1~2 句通用规则 + golden 用例

## 四、结构性改造方案(瘦身之外的根治)

1. **拆〈swap 字段映射与枚举规范〉共享文件**:image_extract 与 place_order 本质是同一任务(输出同一 schema,字段规则语义重叠 ≈8-10K),excel 亦然。三链 system = 共享规范 + 各自"输入形态解析"前置段。一处修规则、三链同步,消除已发生的三链漂移(excel 有 relativeTimeMinutes 而 image 没有;image 内部 priceType 继承与零默认互相矛盾)。再省 ≈8K。
2. **5 个 orderId 节点去 LLM 化**:cancel/query/confirm×3 改为确定性函数(正则 + 去重 + 范围规则),删 5 个提示词、省 5 次 LLM 调用的延迟与成本。意图仍由 intent 节点判定,不损失能力。
3. **确定性归一下沉**:表格模式判定、量词展开、时间补零、千分位、@过滤、机器人名过滤 → 前/后处理代码(有 `prewash/quote_hints` 先例可循)。
4. **错例转 golden**:所有补丁规则逐条转成 `tests/fixtures/` 用例;瘦身后的提示词由 golden + `langfuse_eval` 守住行为,而不是靠提示词里的禁令堆。
5. **excel 链降 LLM 面**:结构化列代码直拷,LLM 只解析"执行方式"一列。

## 五、实施路径与风险控制

按 `.claude/rules/prompt-management.md` 场景 B(ADR 0003 A/B 共存):

1. **P0 批(零风险档)**:新建 `swap/v2/` 系列(或 `_versions.yaml` 灰度位),先落零风险删除;跑 `python scripts/langfuse_eval.py --local tests/fixtures/golden.jsonl`(swap 子集),PASS 率不得低于 v1 基线;
2. **P1 批(低风险合并 + 去 LLM 化 5 节点)**:每步全量回归 + 新增错例 golden;
3. **P2 批(结构性改造 + 需业务确认项)**:业务方逐条确认硬编码词表处置与低频输入形态取舍;
4. **门槛**:每批 v2 相对 v1 的 eval PASS 率差 ≥0 才推进;显著优于 v1 且业务认可后 v2→v1(ADR 0003);全程在 ADR 0001 D5 处置表登记。

**主要风险**:few-shot 削减可能损失长尾 case 表现(以 golden 扩充对冲);"需业务确认"项误删真实低频能力(以线上流量数据决策);瘦身与 Dify 侧同步问题——若 Dify 工作流仍在运行,需与业务方约定以哪侧为主(建议:瘦身在 LangGraph 侧 v2 灰度验证,达标后反向同步 Dify)。
