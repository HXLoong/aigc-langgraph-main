## 场景 1 · Day 1 团队 Kickoff（45 分钟）

> **目的**：3 人都知道自己的 onboarding issue + 互相认识 + Day 3 之前要交什么。
> **参与者**：Tony + A（资深）+ B（一年）+ C（实习生）
> **形式**：会议室或视频，1 人主持（Tony），全员摄像头开
> **必须在 Day 1 上午开**（让大家下午就能动手）

### 议程（按时间）

#### 0-5 分钟 · 开场（Tony）

- 欢迎 3 人加入
- 一句话项目定位：**"otc-agent 是场外衍生品 AI 指令助手，从 Dify 迁到 LangGraph，目标是部署到客户内部环境"**
- 这周目标：**"3 人都通过 onboarding，并提交第一个 PR"**

#### 5-15 分钟 · 项目结构 30 秒讲解（Tony）

打开屏幕共享，按下面顺序点开：

1. `CLAUDE.md` —— 一句话："这是项目宪法，所有规则在这里"
2. `docs/training/README.md` —— 一句话："这是你们今天要打开的第一个文件"
3. `docs/training/langgraph-handbook.md` —— 一句话："4000 行参考书，按需查"
4. `docs/adr/` —— 一句话："16 份决策记录，重点 0016 是这周才出炉的 M3 范围调整"
5. GitHub Issues 页面 —— 给每人指认自己的 onboarding issue

> **不要**深入讲技术细节——细节让他们自己读手册。这一段只为了让他们"知道东西在哪"。

#### 15-25 分钟 · 每人 onboarding 走读（每人 3 分钟）

按顺序请 3 人**轮流出来对屏**，打开自己的 onboarding issue，**自己念出来**：

- A 念 #25：主线 = #33 客户验证 + ADR 0016 M3.2 准备
- B 念 #26：主线 = #29 swap.hand_to_share + #30 ticker 收尾
- C 念 #27：主线 = #31 +20 golden + #32 cascade 单测

> 让他们自己念是为了**逼他们打开 issue 看一眼**——避免会议结束没人记得自己要干啥。

#### 25-35 分钟 · 协作约定（Tony）

明确 4 件事：

1. **Code review 路径**：B 和 C 的 PR 都先请 A review，A review 完 Tony final approve
2. **Walk-through 安排**：A 在 Day 3 给 B 和 C 各做 30-60 分钟 walk-through（已写在 #25 onboarding）
3. **沟通渠道**：
   - 同步：每天 standup 15 分钟 + 飞书群即时
   - 异步：所有问题留 GitHub issue 评论或 PR 评论（不要私聊解决，让信息可追溯）
4. **环境凭证**：Tony 当场把 `.env` 共享方式告诉大家（密码管理器 / 1Password / 内部 wiki，看你团队习惯）

#### 35-43 分钟 · 答疑

留 8 分钟给三人问问题。如果没人问，主动问：

- A："你之前有没有用过 LangGraph？" / "你 review B/C PR 时有什么顾虑？"
- B："你对 swap 业务熟吗？" / "你写过 pytest 吗？"
- C："你装过 Python 虚拟环境吗？" / "你打开过 GitHub PR 吗？"

> 在 Day 1 暴露技能 gap 比 Day 3 暴露便宜 100 倍。

#### 43-45 分钟 · 收尾

- 重申 Day 3 检查点：3 人各自的 onboarding issue 完成 + 各提一个 PR
- 下次见面：明天 standup（15 分钟），固定时间（推荐每天上午 10:00）

### 产出清单

- [ ] 3 人都知道自己的 onboarding issue 链接
- [ ] 3 人都拿到 .env 凭证
- [ ] 飞书群（或类似）建好，3 人 + Tony 都在
- [ ] 明天 standup 时间订好（日历邀请发出）
- [ ] Tony + A 的 60 分钟 1:1 时间订好（推荐 Day 1 下午）

### 主持人提示

- **不要超过 45 分钟**——超时会让他们觉得"开会很多"，影响动手时间
- **不要技术深讲**——细节让他们自己读，会议只是触发
- **C 实习生可能不敢说话**——主动 cue 他："C，你听明白了吗？哪一段最不确定？"

## 场景 2 · 你 + A 一对一（Day 1 下午，60 分钟）

> **目的**：对齐 #33 客户验证 Epic 的范围 + 启动 ADR 0016 M3.2 准备工作。
> **参与者**：Tony + A
> **形式**：1:1 会议室
> **强烈建议在 Day 1 下午开**——A 才刚听完 kickoff，这时对齐范围最及时

### 议程

#### 0-10 分钟 · ADR 0016 共识

A 此时还没读完 ADR 0016（onboarding Day 2 才要求读），但 1:1 不能等。

请 A 当场打开 `docs/adr/0016-m3-scope-engineering-loop-not-shadow.md`，**A 念一遍**（5 分钟），Tony 补充 3 个要点：

1. M3 不再是 Shadow，shadow 工具留 M4 用
2. M3 = 工程联调闭环（M3.1 mock 已过 / M3.2 真后端联调 / M3.3 真后端 golden 回归）
3. 阻塞点 = 等业务方内网 VPN

#### 10-25 分钟 · 客户环境调研清单（共同 brainstorm）

打开 #33 issue 的"阶段 1 客户环境调研"，每条逐个对：

| 调研项 | 现在知道什么？ | 谁去问？什么时候问到？ |
|---|---|---|
| 客户能否访问外网 | ? | Tony 问商务 |
| 客户走代理吗 | ? | Tony 问客户 IT |
| 堡垒机情况 | ? | Tony 问客户 IT |
| 客户 MySQL 版本 | ? | Tony 问客户 DBA |
| Java 后端 API 地址 | ? | Tony 已知或问客户 dev |
| Qwen API 是否可达 | ? | 等 VPN 接通后 A 测 |
| LangFuse 是否离线打包 | ? | A 调研后给 Tony 决策 |
| 部署形态决策（Docker / 二进制） | 倾向 Docker | A 调研客户 Docker 版本 |

> 把这张表的 raw 内容写成 `docs/customer/customer-env-assessment.md` 草稿（当场建文件，写完会议提交）。

#### 25-40 分钟 · M3.2 准备工作排期

哪些事**不等 VPN 也能做**？让 A 当场列出来：

- [ ] 健康检查端点 `GET /ready`（已有 `/health`）
- [ ] 真后端不可达时的降级开关（环境变量或 feature flag）
- [ ] 离线 pip wheel 打包脚本
- [ ] LangFuse self-hosted 离线 docker-compose 包
- [ ] `.env.customer.template` 起草
- [ ] 部署文档 `docs/deploy/customer-private.md` 起草

> 把这个清单作为 #33 阶段 2 的 sub-task，A 可以在 Day 4 起步（Day 1-3 还在 onboarding）。

#### 40-55 分钟 · 风险与节奏

讨论 3 个问题：

1. **VPN 申请进度**：业务方承诺什么时候到？如果 1 周没到，备选方案？
2. **大模型方案**：客户网络如果不能访问 Qwen API，本地化模型有没有预算 / 资源？
3. **A 的精力分配**：onboarding 3 天 + #33 阶段 1-2 + 给 B/C review，会不会过载？

每个问题给一个明确的"下一步动作"。

#### 55-60 分钟 · 收尾

- 共同确认 #33 阶段 1 调研报告交付时间（推荐 Day 4-5）
- 共同确认每周 1:1 时间（推荐每周一下午同时段）

### 产出清单

- [ ] `docs/customer/customer-env-assessment.md` 草稿建立（即使只有问题没有答案）
- [ ] M3.2 准备工作清单贴到 #33 评论里
- [ ] VPN 申请进度责任人 + 时间点明确
- [ ] 每周 1:1 时间订好

## 场景 3 · 每日 Standup（15 分钟）

> **目的**：暴露阻塞 + 同步进度 + 创造互助机会。
> **参与者**：Tony + A + B + C
> **形式**：站会 / 视频，每人 2-3 分钟，Tony 主持
> **时间**：固定每天上午 10:00（建议）

### 议程

#### 标准三问 + 项目特色三问（每人 2-3 分钟）

每人按顺序回答 6 个问题，Tony 帮忙 timing：

| # | 标准问题 |
|---|---|
| 1 | 昨天完成了什么？（指 PR / commit / golden / 文档） |
| 2 | 今天计划做什么？（要具体到 issue 编号） |
| 3 | 有什么阻塞？（说不出来的话，说"没有") |

| # | 项目特色问题 |
|---|---|
| 4 | 今天有 PR 要交付吗？提交后请 @ 谁 review？ |
| 5 | 今天有需要 review 别人的 PR 吗？ |
| 6 | LangFuse Cloud 上有需要团队看的 trace 吗？（如发现奇怪的 case）|

#### 阻塞处理（剩余时间）

只在 standup 里**识别**阻塞，**不**深入解决。每个阻塞当场决定：

- 阻塞描述
- 由谁主导解决
- 何时复盘

复杂阻塞 → 散会后再开小会，不在 standup 里讨论 30 分钟。

### 主持人提示

- **严格 15 分钟**——超时会让大家排斥每天来开
- **C 实习生很容易"今天什么都没做"**——主动问"卡在哪一步？"
- **A 容易讲技术细节**——打断："这个细节 standup 后再聊，下一位"
- **每周一可以加 1 个问题**："本周目标 / 下周开始 / 上周回顾"

### 跳过 standup 的情况

- 周末
- Tony 出差且未指定代理人 —— 让 A 主持
- 全员忙 PR review 终局阶段（罕见）—— 提前飞书通知

### Standup 的价值不在 standup

> Standup 不是为了让 Tony 知道大家在干嘛（那看 GitHub 即可）。它的价值在于**3 人互相听到对方在做什么**——会自然产生：
> - "你那个问题我昨天遇到过，我帮你看看"
> - "你那个 PR 出来我可以 review"
> - "我也在卡这个，我们一起调研"
>
> 如果团队从来没有互相帮助的迹象，standup 就失效了，要换形式（如 pair programming）。

## 场景 4 · 周中 Checkpoint（Day 4，30 分钟）

> **目的**：盘点周一到周三的进度 + 决定剩余 3 天的优先级 + 拦截 onboarding 没过的人。
> **参与者**：Tony + A + B + C
> **时间**：Day 4 上午 standup 之后接着开，30 分钟

### 议程

#### 0-5 分钟 · 进度盘点

打开 GitHub Issues 页面，3 个 onboarding issue 一个个看：

- [ ] #25 onboarding-A：Day 1-3 检查点是否全 ✅？docs PR 提了吗？
- [ ] #26 onboarding-B：swap.cancel 单测 PR 提了吗？
- [ ] #27 onboarding-C：5 条 golden PR 提了吗？

#### 5-15 分钟 · 没过 onboarding 的人怎么办

按"没过的程度"分类处理：

| 状态 | 应对 |
|---|---|
| 全部 ✅ | 鼓励 + 转入主线任务 |
| Day 1-2 过了，Day 3 PR 没提 | 不算严重，给到 Day 5 提，Tony 当场和本人定时间 |
| Day 1 没过（环境跑不起来） | **严重**——会议后 Tony 或 A 立即 pair 解决，不要让人继续憋一周 |
| 完全没动 | 当场谈：是技能问题、动机问题、还是被其他事打断？必要时调整任务 |

> **重点**：周中暴露问题比周末暴露便宜 100 倍。**不要因为"我不想让人尴尬"而跳过这个环节**。

#### 15-25 分钟 · 主线任务排序

确认 Day 4-7 每人的主线任务：

- A：onboarding 收尾 + #33 阶段 1 调研启动 + 给 B/C 第一个 PR review
- B：onboarding 收尾 + #29 swap.hand_to_share 起步
- C：onboarding 收尾 + #31 golden 扩充起步

如果有人 onboarding 严重延迟，主线任务相应延后或缩减。

#### 25-30 分钟 · 互相 pair 邀请

主动问："谁需要 pair？谁愿意被 pair？"

常见组合：
- A pair B：在 #29 swap.hand_to_share 设计 30 分钟
- A pair C：在 #31 golden 写 5 条作为示范
- B pair C：互相看 PR

### 产出清单

- [ ] 3 个 onboarding 状态明确（✅ / 延期 / 救火）
- [ ] Day 4-7 每人主线任务确认
- [ ] 至少 1 对 pair 安排（主动促成互助）

## 场景 5 · 周末 Retro（Day 7，30 分钟）

> **目的**：复盘第 1 周 + 调整下周。
> **参与者**：Tony + A + B + C
> **时间**：Day 7 下午（周五），30 分钟

### 议程

#### 0-10 分钟 · 数字盘点（Tony 准备）

会前 Tony 准备好这些数字（10 分钟工作量）：

| 指标 | 本周值 |
|---|---|
| 合并 PR 数 | ? |
| 新增 golden case 数 | ? |
| harness PASS 率变化 | ? → ? |
| 关闭的 issue 数 | ? |
| 最长 PR review 周期 | ? 天 |
| LangFuse Cloud trace 数 | ? |

会上一起看，不评判，只看数字。

#### 10-20 分钟 · 每人 1 分钟复盘（轮流）

每人回答 3 个问题：

1. 这周做得最满意的一件事？
2. 这周最受挫的一件事？
3. 下周想试什么不一样的？

> 不评论别人的回答。听完所有人之后再统一讨论。

#### 20-25 分钟 · 流程改进

只问 1 个问题：

> "如果只能改一件流程上的事，是什么？"

每人投 1 票，得票最高的下周试。

常见可能：
- standup 时间点不合适
- review 周期太长
- 文档不够清晰
- 任务颗粒度不合适
- 飞书消息太多 / 太少

#### 25-30 分钟 · 下周排期

简单宣布：

- 下周谁的主线任务变化（B 完成 #29 转 #30 等）
- 下周关键里程碑（如 #33 阶段 1 调研报告交付）
- 下周需要重点关注的事

### 产出清单

- [ ] 数字记录到团队 wiki / 飞书文档
- [ ] 流程改进项明确（不超过 1 个）
- [ ] 下周排期明确

### 不要做的事

- ❌ 个人批评（**永远不要在 retro 里点名批评**，私下 1:1 处理）
- ❌ 长篇技术讨论（散会后开技术会）
- ❌ "下周一定要做完 XYZ" 的承诺压力（标里程碑就够了）

## 附录 · 常见情况应对

### A.1 实习生 C 第一天环境跑不起来怎么办

**症状**：Day 1 standup C 说"环境装了一天，pytest 还没跑通"

**不要做**：
- ❌ 当场让 A 帮他装（会让 C 没机会自己学）
- ❌ 跳过让 C "明天继续装" （第二天大概率还是装不通）
- ❌ 在群里问"哪一步报错"（截图来回 30 分钟）

**应该做**：
- ✅ 散会后 A pair C 1 小时（屏幕共享，A 看着 C 装）
- ✅ A 在 1 小时内不能搞定的话，临时给 C 一台公司云开发机（远程 SSH）
- ✅ 把 C 的踩坑写到 `docs/TROUBLESHOOTING.md`，下次新人受益

### A.2 A 的 docs PR 一周没提怎么办

**症状**：Day 5 还没看到 A 的 onboarding 文档 PR

**含义**：A 大概率没真读完 4000 行手册（onboarding Day 2 检查点）

**应对**：
- 1:1 直接问："手册第 X 章你印象最深的是什么？"
- 如果说不出来 → 让 A 重读关键章节（不要假装过了）
- 如果说得出来 → 让 A 当场写一个改进点也行（不必憋大 PR）

### A.3 B 的 swap.cancel 单测 mock 写错了

**症状**：B 提的 PR，CI 报错 "fixture not found" 或 "AsyncMock not awaited"

**含义**：B 没看手册附录 A.3 Mock 陷阱

**应对**：
- A code review 时**不要直接给答案**，留 comment："这里看手册附录 A.3，对应到我们这个 case 该怎么改？"
- 让 B 自己 fix，下次就记住了
- 直接给答案 = 培养"等 reviewer 帮我改"的依赖性

### A.4 业务方内网 VPN 一周没下来

**症状**：#33 阶段 1 调研中"等 VPN"始终红色

**应对**：
- Tony 在每周 1:1 上明确"还没拿到 VPN，谁能帮上忙"——可能要升级到客户更高层
- 并行推进**不依赖 VPN 的 M3.2 准备工作**（健康检查 / 离线打包等）—— 见你 + A 1:1 议程
- 准备 fallback 方案：客户能否提供测试环境的 sandbox URL（比 VPN 阻塞少一层）

### A.5 团队没有人说阻塞，但进度明显慢

**症状**：standup 大家都说"没阻塞"，但周中 checkpoint 发现 PR 没出来

**含义**：可能是文化问题（不敢说），也可能是任务定义模糊（不知道该做什么）

**应对**：
- 1:1 问每个人"如果时间无限你想先做什么？"——暴露真正的迷茫点
- 检查 issue 描述是否够具体（拆得更细的 sub-task）
- standup 里换个问法："今天什么事最让你不确定？"（避免"阻塞"这个词的心理压力）

### A.6 review 队列堆积（A 来不及 review）

**症状**：3 人都提了 PR，A 一周内 review 不完

**应对**：
- 临时引入 cross-review：B 也 review C 的 PR，C 也 review B 的（学习机会）
- A 只做最终 approve（节省时间）
- 严重时 Tony 亲自 review 1-2 个

### A.7 实习生写的 golden case 业务方说不对

**症状**：C 提的 golden case，PM review 说"不符合业务真实表达"

**应对**：
- 不要让 C 重写（容易气馁），而是请 PM 当场改 1-2 条做示范
- 把 PM 改后的版本作为 C 后续写 case 的 reference
- 这是"师徒制"，比文档好用

### A.8 周末有人加班

**应对**：

- **明令禁止**强制加班
- 如果有人主动加班，周一 1:1 问清楚原因（任务过重？想表现？兴趣驱动？）
- 任务过重 → 减任务
- 想表现 / 兴趣驱动 → 引导用补休 / 升级方向
- **不要表扬加班行为**，会引发竞争性加班

## 这份 playbook 怎么用

- 第 1 周严格按这 5 个场景跑一遍
- 第 2 周开始按效果裁剪：
  - 场景 1（kickoff）只第 1 周用
  - 场景 2（你+A 1:1）保持每周
  - 场景 3（standup）保持每天
  - 场景 4（周中 checkpoint）保持每周
  - 场景 5（retro）保持每周
- 每场景超时 50% 以上 → 议程要瘦身
- 每场景没产出 → 议程要替换
- 团队稳定后（4-6 周后）可以让 A 主持 standup，Tony 只参加周中和周末

> 这份文档自己也是活的——把你们的实战经验写进附录 A，下次新人/新项目复用。
