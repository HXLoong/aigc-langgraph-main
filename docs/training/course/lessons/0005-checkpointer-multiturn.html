LangGraph 团队实战课 · 第 05 课

Checkpointer 与多轮对话

客户第一句"给我下单平安银行"，第二句只回"确认"——机器人凭什么记得上一句？答案是 checkpointer。本课讲清恢复语义、thread_id 约定，以及一个坑掉过真实生产 case 的陷阱。

编写者：图灵科技预计用时：25 分钟前置：第 04 课小测全对
为什么学这个（对齐任务） 业务流程几乎全是多轮的：下单 → 补参数 → 确认下单，跨 2-4 条企微消息。Dify 里这靠"会话变量"（conversation_variables，平台黑盒）；LangGraph 里是 checkpointer——整个 state 每步自动落库，同一 thread_id 自动恢复。M3 错例里"多轮 tickers/params 丢失"一类根因全和本课内容有关。

1. 恢复语义：state 是"续写"不是"新建"（8 分钟）

机制一句话：每个节点跑完，全量 state 快照写入存储；下次同一个 thread_id 调 ainvoke，新输入合并到上次的 state 上继续跑。

# 第 1 轮：客户说"下单平安银行 5000 股"
config = {"configurable": {"thread_id": "room-42-cust-7"}}
await graph.ainvoke({"raw_text": "下单平安银行 5000 股", ...}, config=config)
# 跑完后 checkpoint 里已有：tickers=[000001.SZ...], place_params={...}, intent="place_order_request"

# 第 2 轮：客户只说"确认"
await graph.ainvoke({"raw_text": "确认", ...}, config=config)
# 图启动时 state 已经带着第 1 轮的 tickers / place_params —— 不用重新提取！

合并规则就是第 01 课的 reducer 语义：覆盖型字段（raw_text）被新输入覆盖；累加型字段（history_messages / trace）继续追加。这也解释了 CLAUDE.md 排查表里那句"trace 是累积的，多轮 case 的本轮节点在末尾"。

高频真实根因：初始 state 覆盖 checkpoint CLAUDE.md"常见根因模式"表里有两条都是它："reply 含'无法识别'但未问标的 → make_initial_state 设了 tickers=[] 覆盖 checkpoint"、"多轮 tickers/params 丢失 → make_initial_state 不应对业务字段设默认值"。原理：你在第 2 轮的初始 state 里写了 tickers=[]，覆盖型合并就会把 checkpoint 里第 1 轮辛苦提取的标的冲掉。结论：初始 state 只放本轮输入字段，业务字段一律不给默认值。

2. thread_id 约定与生产接线（7 分钟）

API 层真实代码——thread_id 就是请求里的 user 字段（Java 侧传的 conversation_id）：

initial_state = _inputs_to_state(req.inputs, fallback_conversation_id=req.user)
config = {"configurable": {"thread_id": req.user}}
final_state: AgentState = await graph.ainvoke(initial_state, config=config)
app/api/routes.py:92-98

项目约定：thread_id 固定 = conversation_id（企微会话 ID）。同群同客户共享历史；换群/换客户 → 不同 thread_id → state 完全隔离。

生产用 MySQL 存储，生命周期绑定 FastAPI lifespan（应用级单例，不要每个请求新建）：

async def init_checkpointer() -> AIOMySQLSaver:
    _saver_ctx = AIOMySQLSaver.from_conn_string(settings.mysql_uri)
    _checkpointer = await _saver_ctx.__aenter__()
    await _checkpointer.setup()      # 首次启动自动建 4 张系统表（幂等）
    return _checkpointer

3. Interrupt：下单前的人工确认（4 分钟）

checkpointer 的存在让"暂停-恢复"成为可能。编译时声明在哪些节点前暂停：

graph = g.compile(
    checkpointer=cp,
    interrupt_before=["call_swap_api"],   # 真实下单前暂停，等人工确认
)

# 第一次 ainvoke：跑到该节点前停下，state 已落 checkpoint
# 人工确认后：ainvoke(None, config)  ← None = 不加新输入，从断点继续

项目边界（ADR 0006）：HITL 只用于业务参数二次确认（如下单前确认卡片），不用于 LLM 解析失败兜底——那是第 03 课 fallback 链路的职责。两条路线别混。

4. 动手实验（6 分钟）

实验：亲眼看见记忆的延续与冲掉

  1. 取第 01 课的玩具图，编译时传 InMemorySaver：graph = g.compile(checkpointer=InMemorySaver())
  2. 用同一个 config = {"configurable": {"thread_id": "t1"}} 连续 ainvoke({"counter": 0}) 两次，观察第二次的 counter 和 log——为什么 counter 没有从 3 继续涨？（提示：你第二次传入的 {"counter": 0} 对覆盖型字段意味着什么）
  3. 第三次调用改传 {}（空输入），再观察——这回从 checkpoint 恢复的 counter 生效了吗？
  4. 把三次的输出和你的解释发给助教。这个实验做透了，第 1 节那个"生产真实根因"你就永远不会踩

5. 小测（拿到全对再进第 06 课）

自测 · 4 题

1. 同一客户在同一个企微群的第 2 条消息，图启动时的 state 是什么？

thread_id 相同 → 从 checkpoint 恢复全量 state，新输入按 reducer 规则合并（覆盖型覆盖、累加型追加）。这是多轮对话不用重复提参的根本机制。

2. 第 2 轮的初始 state 里给业务字段写了 tickers=[]，后果是？

tickers 是覆盖型字段（没挂 reducer），传入 [] 就是"用空值覆盖"。这是 CLAUDE.md 常见根因表里的真实生产 bug——初始 state 不要给业务字段设默认值。

3. 忘了给 compile() 传 checkpointer，最先观察到的症状是？

不传 checkpointer 完全合法（单轮场景够用），所以这个错不报警、只在多轮时静默失忆——最阴险的一类 bug（.claude/rules/langgraph-patterns.md 明确列为陷阱）。

4. 恢复被 interrupt_before 暂停的图，正确调用是？

None 是专门的信号："不新增输入，从 checkpoint 继续"。传完整 state 或 {} 都会被当成新一轮输入做合并，语义完全不同（handbook 第 2.9 节）。
