LangGraph 团队实战课 · 第 05 课

Checkpointer 与多轮对话

客户第一句"给我下单平安银行"，第二句只回"确认"——机器人凭什么记得上一句？答案是 checkpointer。本课讲清恢复语义、thread_id 约定，以及一个坑掉过真实生产 case 的陷阱。

编写者：图灵科技预计用时：25 分钟前置：第 04 课小测全对
为什么学这个（对齐任务） 业务流程几乎全是多轮的：下单 → 补参数 → 确认下单，跨 2-4 条企微消息。LangGraph 里靠 checkpointer 把 state 落库，同一 thread_id 自动恢复；但本项目刻意规定哪些字段跨轮保留、哪些每轮清空——搞错这一点，就会出现"上一轮的订单被这一轮误用"的 bug。

1. 恢复语义：哪些跨轮保留，哪些每轮清空（8 分钟）

机制一句话：每个节点跑完，state 快照写入存储；下次同一个 thread_id 调 ainvoke，新输入合并到上次的 state 上继续跑。在此之上，本项目按生命周期给字段分层（ADR 0024 D2）：

层典型字段跨轮行为
本轮输入raw_text / quote_content / message_id每轮由 API 入口全量写入
会话记忆history_messages、last_confirmed_params跨轮保留（历史按窗口截断）
业务对象place_params / cancel_params / confirm / close_params每轮由 ingest 清空
工程字段trace / error / trace_id每轮清空
# 第 1 轮：客户说"下单平安银行 5000 股"
config = {"configurable": {"thread_id": "conv-42"}}
await graph.ainvoke(inputs_to_state(turn1_inputs), config=config)
# 后端生成待确认卡片；history_messages 记下本轮原话与回复

# 第 2 轮：客户引用卡片回复"确认下单"
await graph.ainvoke(inputs_to_state(turn2_inputs), config=config)
# ingest 先清空上一轮的 place_params 等业务对象；确认节点从本轮引用的卡片里取订单号

为什么业务对象要每轮清空：如果上一轮的 place_params 残留到下一轮，render 会把它当成本轮结果渲染，或让确认动作作用到客户没有引用的订单上。跨轮上下文只靠 history_messages 和 last_confirmed_params（仅作上下文，不能替代用户引用）。

一轮输入只有一个入口 app/api/turn_state.py::inputs_to_state 是一轮输入 → AgentState 的唯一入口，生产与评测共用；本轮输入字段缺省时显式置空，不从 checkpoint 继承。不要在别处手工拼初始 state。

2. thread_id 约定与生产接线（7 分钟）

API 层代码——thread_id 取请求里的 conversation_id：

initial_state = inputs_to_state(req.inputs)
config = {"configurable": {"thread_id": conversation_id}}
final_state: AgentState = await graph.ainvoke(initial_state, config=config)
app/api/routes.py（简化）

项目约定：thread_id 固定 = conversation_id（企微会话 ID）。同群同客户共享历史；换群/换客户 → 不同 thread_id → state 完全隔离。

生产用 MySQL 存储，生命周期绑定 FastAPI lifespan（应用级单例，不要每个请求新建）：

# app/checkpointer/factory.py（简化）
pool = await aiomysql.create_pool(..., pool_recycle=1800)   # 连接池，回收时间小于 wait_timeout
saver = AIOMySQLSaver(conn=pool, serde=白名单序列化器)
# 表由 sql/init.sql 预先创建；启动时只读校验表结构，不在运行期调用 setup()

3. 为什么本项目不用 interrupt（4 分钟）

LangGraph 支持用 interrupt_before 在某节点前暂停、人工确认后用 ainvoke(None, config) 从断点继续。本项目不用它（ADR 0021）：写操作的二次确认统一走文本二阶段——第一轮后端生成待确认卡片并结束本轮，客户下一条消息"确认 + 引用订单"时才真正写后端。这样每条消息都是一次完整的图执行，不依赖断点恢复，也不需要企微按钮回调。

checkpointer 在本项目里的作用是跨轮保留会话记忆，不是暂停-恢复。

4. 动手实验（6 分钟）

实验：亲眼看见记忆的延续与冲掉

  1. 取第 01 课的玩具图，编译时传 InMemorySaver：graph = g.compile(checkpointer=InMemorySaver())
  2. 用同一个 config = {"configurable": {"thread_id": "t1"}} 连续 ainvoke({"counter": 0}) 两次，观察第二次的 counter 和 log——为什么 counter 没有从 3 继续涨？（提示：你第二次传入的 {"counter": 0} 对覆盖型字段意味着什么）
  3. 第三次调用改传 {}（空输入），再观察——这回从 checkpoint 恢复的 counter 生效了吗？
  4. 把三次的输出和你的解释发给助教。想清楚"传入的值会覆盖 checkpoint 里的同名字段"，就能理解为什么本项目只允许 inputs_to_state 一个入口写本轮输入

5. 小测（拿到全对再进第 06 课）

自测 · 4 题

1. 同一会话的第 2 条消息进入主图、经过 ingest 之后，下列哪项仍保留着上一轮的内容？

业务对象和 trace 每轮由 ingest 清空；跨轮只保留会话记忆（history_messages、last_confirmed_params）。

2. 为什么业务对象（如 place_params）要每轮清空？

残留的业务对象会被 render 当成本轮结果，或让确认动作作用到客户没有引用的订单上（ADR 0024 D2）。

3. 忘了给 compile() 传 checkpointer，最先观察到的症状是？

不传 checkpointer 完全合法（单轮场景够用），所以这个错不报警、只在多轮时静默失忆——最阴险的一类 bug（.claude/rules/langgraph-patterns.md 明确列为陷阱）。

4. 本项目里客户下单后的二次确认是怎么实现的？

文本二阶段确认（ADR 0021）：每条消息都是一次完整的图执行，不依赖断点恢复。
