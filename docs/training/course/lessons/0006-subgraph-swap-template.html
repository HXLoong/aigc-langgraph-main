子图模板：以 swap 为例

前五课的所有零件，今天拼成一个完整业务子图。swap 是全项目的标准模板——学会它，option / close 一眼就能看懂，未来新产品子图照葫芦画瓢。

编写者：图灵科技预计用时：30 分钟前置：第 05 课小测全对
为什么学这个（对齐任务） Dify 时代加一类业务 = 在 12957 行主干 YAML 里拖节点连线；LangGraph 时代 = 新建一个目录，五步组装，主图加一行。团队的"节点级 PR"协作模式（一人一节点互不冲突）就建立在这个结构上。这也是 subgraph-builder agent 干活的底层套路。

2. 五步组装法（12 分钟）

第 1 步 · models.py：先定契约

意图枚举 SwapIntentType（7 值，与 Java SwapIntentionType 对齐）+ 各节点的输出模型。先写模型再写节点——模型就是节点间、以及与后端的契约（第 04 课件套三）。

第 2 步 · intent.py：二级意图分类

第 04 课整课讲的就是它。输入 raw_text / quote_content / history，输出 state["intent"]。

第 3 步 · 业务节点 × N

每个意图一个 .py 文件（confirm 例外：3 个确认子意图合并 1 节点，这是 ADR 0001 D5 登记过的改写）。全部遵守：@safe_node + 三件套 + 返回 partial dict 写入按业务聚合的字段（place_params / cancel_params / confirm……，不是 swap_place_order_output 这种按节点铺开的字段——ADR 0001 D6）。

第 4 步 · graph.py：组装

def build_swap_graph() -> CompiledStateGraph:
    g: StateGraph = StateGraph(AgentState)          # 与主图共享同一个 State schema！
    g.add_node("swap_intent", swap_intent)
    g.add_node("swap_place_order", swap_place_order)
    g.add_node("swap_confirm", swap_confirm)
    g.add_node("swap_cancel", swap_cancel)
    g.add_node("swap_query_order", swap_query_order)
    g.add_node("swap_unknown", swap_unknown)

    g.add_edge(START, "swap_intent")
    g.add_conditional_edges("swap_intent", _route_after_swap_intent, {...})  # 第 02 课的路由表
    for n in ("swap_place_order", "swap_confirm", "swap_cancel",
              "swap_query_order", "swap_unknown"):
        g.add_edge(n, END)
    return g.compile()

共享 State 的含义 子图和主图都用 AgentState：主图写的字段（raw_text / product_type）子图直接读，子图写的字段（intent / place_params / tickers）自动回传主图，render 节点统一消费。LangGraph 也支持子图用独立 schema + 输入输出转换（官方 Subgraphs 文档），但本项目刻意全部共享——少一层映射，少一类 bug。

3. 两条设计纪律（5 分钟）

  1. 意图全覆盖 + 兜底：路由表覆盖 7 个意图中的 6 个，第 7 个 unknown_intent 和一切表外值都落到 swap_unknown。任何子图都必须有这个"意图收容所"，保证 LLM 输出什么都有地方去。
  2. 特例节点也是节点：swap_unknown 就定义在 graph.py 里（10 行，只写 trace），照样戴 @safe_node。不要因为节点简单就跳过规范。

另外注意：标的（证券代码 / 名称）不在 LangGraph 里识别——业务节点只提取客户原文，交给 Java 后端的标的工具权威识别（ADR 0025）。

5. 小测（拿到全对再进第 07 课）

自测 · 4 题

1. 子图写入的 place_params，主图的 render 节点为什么能直接读到？

两边都是 StateGraph(AgentState)，子图节点返回的 partial dict 合并进的就是同一份 state——没有"拷贝/同步"这一步。

2. State 字段"按业务对象聚合、不按节点铺开"（ADR 0001 D6）的核心好处是？

swap 和 option 的下单节点都写 place_params，render 统一读——如果按节点铺开成 24 个 output 字段，render 要写 24 个分支。（"重名覆盖"恰恰是聚合刻意利用的特性，不是要避免的问题。）

3. 新增一个业务子图，下面哪件事不需要做？

本项目子图一律共享 AgentState（新业务字段加进同一个 TypedDict）。a 和 c 都必须做，另外还有 prompts 目录、golden case、测试。

4. 为什么每个子图都必须有 swap_unknown 这样的兜底节点？

unknown_intent 是合法意图值 + LLM 可能输出表外值 + cascade 错误也路由到它——三类"没人接"的情况都要有确定去处，图才永不卡死。（b 说反了：错误出口是它的职责之一，但不是"必须存在"的原因——主图 fallback 也能兜。）
