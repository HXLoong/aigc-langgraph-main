LangGraph 团队实战课 · 第 04 课

LLM 三件套：load_prompt + with_structured_output + Pydantic

项目里 20+ 个 LLM 节点全是同一个模板。学完本课，你能独立写出一个规范的 LLM 节点——这是领第一个 issue 的最低门槛。

编写者：图灵科技预计用时：30 分钟前置：第 03 课小测全对
为什么学这个（对齐任务） Dify 的 LLM 节点 = YAML 里嵌几千行 prompt + 内嵌 JSON Schema。迁移后拆成三件：提示词（.md 资产，来自 Dify 导出）、输出模型（Pydantic，对齐 Java DTO）、节点函数（10 行胶水）。这个拆法让业务方能改 .md、后端能对 DTO、工程能测函数——三方并行工作，这正是我们迁出 Dify 的核心理由。

2. 件套一：load_prompt 的三个必知点（8 分钟）

2.1 .md 文件格式与来源

提示词是从 Dify YAML 导出的资产，放 app/prompts/<category>/<name>.md，格式约定：## [system] 与 ## [user] 两段代码块。注意目录名陷阱：提示词目录是 option_close/，代码目录是 subgraphs/close/，两边不对称（沿用 Dify 命名，app/prompts/CLAUDE.md）。

Dify 占位符 {{#node_id.var#}} 保留原样，不要 regex 替换——LLM 能理解为上下文标记，替换反而破坏与 Dify 的行为对齐。

2.2 lru_cache 陷阱（高频踩坑）

@lru_cache(maxsize=128)
def load_prompt(category: str, name: str) -> Prompt: ...
app/prompts/__init__.py:128

启动后重复加载零成本——代价是改了 .md 不重启就不生效。测试里改提示词后要 from app.prompts import clear_cache; clear_cache()。"改了提示词没效果"九成是这个。

2.3 来源优先级（ADR 0014）

ENABLE_LANGFUSE=true 且 use_langfuse_prompts=true 时优先从 LangFuse 拉（运行时可热更、可灰度晋升），失败自动回退本地 .md。所以生产行为可能和你本地 .md 不同——排查提示词问题先确认当时加载的是哪个来源（trace 里记了 prompt_name）。

3. 件套二：LLM 工厂——为什么不许自己 new ChatOpenAI（7 分钟）

所有节点从 app/llm/clients.py 的工厂拿 LLM（get_qwen_standard / thinking / structured / complex / vl）。名字里的 qwen 是历史命名——ADR 0020 起现场统一 DeepSeek-V4-pro，vendor 由 .env 切换。工厂里封了两个 vendor 适配，自己 new 就会绕过它们：

# 适配一：统一关闭思考模式（速度：4-7s vs thinking 60-180s），两家参数不同
def _thinking_off_extra_body(model: str) -> dict[str, Any]:
    if _is_deepseek(model):
        return {"thinking": {"type": "disabled"}}   # DeepSeek 会静默忽略 Qwen 的参数！
    return {"enable_thinking": False}

# 适配二：DeepSeek 不支持 response_format=json_schema（400 报错），
# 统一把 with_structured_output 降级为 function_calling
class _ChatLLM(ChatOpenAI):
    def with_structured_output(self, schema=None, **kwargs):
        if _is_deepseek(self.model_name) and "method" not in kwargs:
            kwargs["method"] = "function_calling"
        return super().with_structured_output(schema, **kwargs)

4. 件套三补充：为什么绝不手工 json.loads（3 分钟）

手工 json.loads(response.content)with_structured_output(Model)
LLM 输出裹了 ```json 围栏解析失败，节点挂框架处理，拿到干净对象
字段类型错（"5000股"→int）下游才炸，难定位Pydantic 当场校验 + 自带 1 次重试
重试仍失败各节点自造轮子抛 ValidationError → @safe_node 兜底 → fallback（第 03 课链路）
静态检查dict 取值全靠猜result.type 有类型提示，mypy 保护

6. 小测（拿到全对再进第 05 课）

自测 · 4 题

1. 你改了 app/prompts/swap/intent.md，重跑正在运行的服务里的请求发现行为没变，最可能的原因是？

三个都可能，但最高频的是 lru_cache（handbook 附录 A.10）。排查顺序：先重启/clear_cache，再看 trace 里的 prompt 来源，最后查格式。

2. LLM 输出不符合 Pydantic schema 时，第一道处理是什么？

顺序是：框架重试 1 次 → 仍失败抛 ValidationError → @safe_node 兜底写 error → cascade 走 fallback。不走 HITL（CLAUDE.md 核心原则第 8 条）。

3. 为什么必须从 app/llm/clients.py 工厂拿 LLM，而不是节点里自己 ChatOpenAI(...)？

自己 new 会绕过 _thinking_off_extra_body（DeepSeek 默认开思考 → 延迟 60-180s）和 _ChatLLM 的 function_calling 降级（json_schema 直接 400）——两个都是线上真实踩过的坑（ADR 0020）。另外 lru_cache 单例还省了重复建连接池。

4. 参数提取模型 SwapOrderItem（19 个字段）的 extra 策略应该选哪个，为什么？

大 schema 下 LLM 经常多吐一两个顶层字段；forbid 会让本来正确的提取因此重试甚至失败。意图类小输出才用 forbid（swap/models.py 两种用法并存）。
