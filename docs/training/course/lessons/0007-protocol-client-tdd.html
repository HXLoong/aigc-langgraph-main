Protocol Client 与 TDD

Dify 时代最大的痛是"没法测试"。本课学两件事：后端调用为什么走 Protocol（以及它怎么让测试成为可能），和项目强制的 TDD 红绿流程——外加一个坑掉过无数人的 mock 陷阱。

编写者：图灵科技预计用时：30 分钟前置：第 06 课小测全对
为什么学这个（对齐任务） "可严肃测试"是我们迁出 Dify 的第一理由（ADR 0000），数千个测试就是成果。但这套体系有两条纪律撑着：依赖反转（后端可 mock）和 TDD 强制（CLAUDE.md 核心原则第 5 条：先写失败测试再改代码，禁止反过来）。你的每一个 PR 都会被用这两条检验。

2. mock 陷阱：patch 使用点，不是定义处（8 分钟）

全项目最高频的测试坑（tests/CLAUDE.md 专页警告）。原理一句话：from x import y 会把 y 这个名字绑进当前模块，此后 patch 原模块的 x.y 改不到这个已绑定的名字。

# ❌ 不生效：patch 定义处
monkeypatch.setattr("app.llm.clients.get_qwen_thinking", fake)
# swap/intent.py 早就 `from app.llm.clients import get_qwen_thinking`，名字已绑到 intent 模块

# ✅ 生效：patch 使用点（intent 模块里的名字）
monkeypatch.setattr("app.subgraphs.swap.intent.get_qwen_thinking", fake)

再看项目里 mock LLM 的标准写法——注意 mock 链要还原 with_structured_output 的调用形状：

def _patch_llm(monkeypatch, return_type: str) -> AsyncMock:
    """让 swap.intent 调 LLM 时返回固定 SwapIntentOutput。"""
    fake_output = SwapIntentOutput(type=return_type)          # mock 到 Pydantic 实例，不是 JSON 字符串！

    fake_llm_with_schema = MagicMock()
    fake_llm_with_schema.ainvoke = AsyncMock(return_value=fake_output)

    fake_base_llm = MagicMock()
    fake_base_llm.with_structured_output = MagicMock(return_value=fake_llm_with_schema)

    monkeypatch.setattr(intent_module, "get_qwen_thinking", lambda: fake_base_llm)  # 使用点！
    return fake_llm_with_schema.ainvoke

# 用法：节点函数直接当普通 async 函数测，连图都不用建
async def test_classifies_place_order(monkeypatch):
    _patch_llm(monkeypatch, "place_order_request")
    result = await swap_intent({"raw_text": "做一笔招商银行的 TRS"})
    assert result["intent"] == "place_order_request"

3. TDD 红绿流程（6 分钟）

项目强制顺序（禁止先改代码再补测试，禁止跳过 RED 验证）：

# 1. 写最小复现测试（体现 bug 或新需求的期望行为）
# 2. 跑到 RED —— 必须亲眼看到它失败
.venv/bin/python -m pytest tests/subgraphs/swap/test_yyy.py -v
# 3. 写最小修复代码
# 4. 跑到 GREEN + 全量回归
.venv/bin/python -m pytest tests/ -q --tb=line 2>&1 | tail -5
为什么 RED 这一步不能省 没见过测试失败，你就不知道它是否真的在测你以为在测的东西——一个从写出来就绿的测试，很可能 mock 错了位置（比如 patch 了定义处），改什么都绿。RED 是测试自身的测试。三层金字塔（模型/路由单测 → 子图节点测 → E2E）与更多技巧见 .claude/rules/testing.md。

4. 动手练习：完整走一遍红绿（8 分钟）

练习：给 swap_cancel 写一个新测试

  1. 模仿 test_intent.py 的 _patch_llm 写法，给 swap_cancel 节点写一个"取消意图正确写入 cancel_params"的测试（先读 app/subgraphs/swap/cancel.py 确认它的 LLM 工厂名和输出模型）
  2. 故意先把 patch 目标写成定义处 app.llm.clients....，跑一遍——观察测试是怎么"错着绿"或者报错的，体感一次陷阱
  3. 改成使用点，跑到真 GREEN；再全量 pytest tests/subgraphs/swap/ -v 确认没破坏别的
  4. 把两次运行的差异和你的解释发助教

5. 小测（拿到全对再进第 08 课）

自测 · 4 题

1. 节点里为什么禁止直接 httpx.AsyncClient 调后端？

依赖反转：节点依赖接口，测试塞 FakeClient、生产用 Httpx 实现（内聚了认证头/tenacity 重试/dry_run）。httpx 本身是异步库，a 是错误说法（ADR 0001 D2 修订版）。

2. patch 了 app.llm.clients.get_qwen_thinking 但节点还在调真 LLM，原因是？

"patch where it's looked up"——from x import y 后，y 存在于导入方的命名空间，改原模块无效。要 patch app.subgraphs.swap.intent.get_qwen_thinking（tests/CLAUDE.md 头号陷阱）。

3. mock LLM 时，ainvoke 的返回值应该设成什么？

with_structured_output 之后 ainvoke 返回的就是 Pydantic 实例——mock 要还原这个形状（fake_output = SwapIntentOutput(type=...)），返回字符串会让节点代码 result.type 直接炸（testing.md E2E 节）。

4. 测试太慢，因为它真的在发 HTTP 请求。正确的提速方式是？

mock 属于测试侧：transport 注入 / FakeClient。a（业务代码里内置"备用实现"开关）和 c（autouse 全局绕过真实路径）都被 CLAUDE.md"面向测试编程"红线明令禁止。
