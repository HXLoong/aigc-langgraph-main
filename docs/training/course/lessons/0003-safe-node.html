@safe_node：错误不崩图

项目里每个节点都戴的那顶帽子，今天整个拆开。学完你能解释：为什么节点里禁止裸 try/except、trace 是怎么"自动"出现的、一次异常从抛出到用户看到友好回复的全过程。

编写者：图灵科技预计用时：20 分钟前置：第 02 课小测全对
为什么学这个（对齐任务） 生产环境里 LLM 会超时、后端会 5xx、Pydantic 会校验失败。Dify 时代这些是"平台重试后工作流失败"；LangGraph 时代兜底责任在我们自己代码里。@safe_node 就是全项目统一的兜底层——你写的每个节点都要靠它，review 时"节点没加 @safe_node"是一票否决项（CLAUDE.md 核心原则第 3 条）。

1. 装饰器全文剖析（10 分钟）

app/graph/safe_node.py 一共 91 行，核心是这个 wrapper（真实代码，只删了日志与埋点行）：

def safe_node(fn: NodeFn) -> NodeFn:
    @functools.wraps(fn)
    async def wrapper(state: AgentState) -> dict[str, Any]:
        node_name = fn.__name__
        t0 = time.perf_counter()
        try:
            update = await fn(state)                       # ① 跑真正的节点函数
            elapsed_ms = int((time.perf_counter() - t0) * 1000)

            # ② 自动追加 trace（节点函数没自带 trace 时）
            existing_trace = update.setdefault("trace", [])
            if not any(_is_same_node(entry, node_name) for entry in existing_trace):
                existing_trace.append(TraceEntry(node=node_name, elapsed_ms=elapsed_ms))

            emit_node_completed(node=node_name, status="ok", elapsed_ms=elapsed_ms)
            return update

        except Exception as exc:                           # ③ 兜底：任何异常都不外抛
            emit_node_completed(node=node_name, status="error", elapsed_ms=...)
            return {
                "error": ErrorInfo(
                    node=node_name,
                    type=type(exc).__name__,
                    message=str(exc),
                    traceback=traceback.format_exc(),
                ),
                "trace": [TraceEntry(node=node_name, decision="error", elapsed_ms=...)],
            }
    return wrapper
app/graph/safe_node.py:26-81（节选，日志/埋点细节见原文件）

三个职责逐一看：

职责实现对你写节点的意义
① 异常兜底except Exception → 返回 {"error": ErrorInfo(...)}，节点正常返回节点里不写 try/except；抛出去就是最好的错误处理
② 自动 tracesetdefault("trace", []) + 查重后追加（elapsed_ms 自动计）不关心耗时就别写 trace；要记录决策就自己 append（如 decision="intent=..."），装饰器查重不会重复加
③ 监控埋点emit_node_completed(status="ok"/"error")Prometheus /metrics 的节点成功率/耗时指标免费获得（C1.5）

ErrorInfo 四个字段（app/graph/state.py:56-63）：node（谁失败）/ type（异常类名）/ message / traceback（完整栈，harness 定位用）。

2. 一次异常的完整旅程（5 分钟）

把 02 课的链路加上本课细节，从抛出到用户看到回复：

swap_intent 里 LLM 超时抛 TimeoutError
  ①  @safe_node 捕获 → return {"error": ErrorInfo(node="swap_intent", type="TimeoutError", ...),
                                "trace": [TraceEntry(node="swap_intent", decision="error")]}
  ②  子图路由 _route_after_swap_intent：has_error(state) → "swap_unknown" → 子图结束
  ③  主图继续 persist → render；render 看到 error → reply_text = 友好话术
  ④  API 层（app/api/routes.py:99）：status = "failed" if final_state.get("error") else "succeeded"
      error_msg = final_state["error"].message      ← 调用方（Java）拿到可读错误
两个边界，别理解过头 ① @safe_node 兜的是意外异常；LLM structured output 解析失败先由 with_structured_output 自带 1 次重试，重试仍失败抛 ValidationError 才轮到它兜（第 04 课细讲）。② 它不是业务分支工具——"后端返回订单不存在"是正常业务响应，该在节点里如实处理并透传，不是靠抛异常走 fallback（P0 红线：不掩盖后端真实响应）。

3. 动手实验（5 分钟）

实验：亲手触发一次兜底

  1. 在 scratch 文件里写一个 @safe_node 装饰的节点，函数体只有一行 raise ValueError("boom")
  2. asyncio.run() 调用它（传 {}），打印返回值——确认拿到的是 dict 而不是异常
  3. 检查 error.node / error.type / error.message 三个字段的值，和 trace 里那条 decision="error"
  4. 去掉装饰器再跑一次，感受"图会崩"是什么样

提示：需要 from app.graph.safe_node import safe_node，在仓库根目录用 .venv/bin/python 跑。

4. 小测（拿到全对再进第 04 课）

自测 · 4 题

1. 节点函数里为什么禁止自己写 try: ... except: pass？

异常被节点自己吞掉，@safe_node 就捕不到，state["error"] 不会写入，cascade 防御和 API 的 failed 状态全部失灵——错误被静默掩盖是最难排查的故障。

2. 节点自己往返回值里写了 trace（带 decision），装饰器还会再追加一条同节点的 TraceEntry 吗？

if not any(_is_same_node(entry, node_name) ...)——已有同名条目就不追加，所以自带 decision 的 trace 不会出现重复（safe_node.py:47-51）。

3. 一个节点抛了异常，API 最终返回给 Java 调用方的是什么？

图不崩、正常走完并返回 Dify 协议响应，status="failed" + error.message（app/api/routes.py:99-104）。500 只发生在图外层的意外（也被 routes 的 except 转成 failed）。

4. 后端接口返回了业务错误"订单不存在"，节点应该怎么处理？

"订单不存在"是后端的真实业务响应，不是系统故障——@safe_node 只兜意外异常。改写后端响应触碰 P0 红线"不掩盖后端真实响应"（CLAUDE.md 绝对禁止清单）。
