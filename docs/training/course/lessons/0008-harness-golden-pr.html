LangGraph 团队实战课 · 第 08 课（最终课）

harness 与 golden case：你的第一个 PR

测试保证"代码没写错"，评估保证"机器人没答错"——这是两套体系。本课学会跑评估、顺 trace 定位失败节点，以及"节点级 PR"的完整交付标准。学完这课，课程毕业，实战开始。

编写者：图灵科技预计用时：30 分钟前置：第 07 课小测全对
为什么学这个（对齐任务） 日常核心工作就是"数据集回归 + 错例修复"（ADR 0030 D3 评测门）。你改任何提示词或节点，唯一能回答"有没有回归"的就是数据集评估：意图集只调 LLM，业务集 388 条走本地 HTTP 入口——会用这套是参与日常迭代的入场券。

1. golden case：期望行为的数据化（7 分钟）

tests/fixtures/categories/*.jsonl 每行一条 case，真实样例（case-030 节选）：

{
  "caseNo": "case-030",
  "category": "option_close_case",
  "description": "查持仓后第一笔限价全平并确认",
  "send_text": "我想平仓",
  "expected": {"product_type": "option_close", "intent": "close_order_query"},
  "response_contains": ["以下是您的期权持仓", "合约编号："],
  "sub_scenes": [
    {"send_text": "第一笔，限价10，全平", "quote_previous": true, ……}
  ]
}
tests/fixtures/categories/golden_option_close_case.jsonl（sub_scenes 即后续轮次）

case 分三桶维护，退出门不同：

桶来源PASS 门槛
B业务方手写种子（主基线，意图均衡）≥ 90%
CLLM 对抗式 paraphrase（harness/case_generator/，边界 case）≥ 80%
D客户历史真实输入（须业务方标注 expected 后合入）持续累积，无硬门槛

纪律：新增节点/意图必须同步加 golden case（每节点至少 5 条），禁止"先合代码、稍后补 case"。

2. 两个评估入口（8 分钟）

入口一：langfuse_eval.py —— 带 DeepSeek Judge

# 意图集（只调 LLM + 仓库内 mock 后端，CI 同款）
python scripts/langfuse/langfuse_eval.py --local tests/fixtures/intent --concurrency 3 --fail-under 0.95
# 只跑受影响的 case（日常迭代）
python scripts/langfuse/langfuse_eval.py --local tests/fixtures/categories --ids case-025,case-026 --concurrency 2

每条 case 由 DeepSeek Judge 打分（score + judge_comment），并把 per-turn 富集 JSON 写入 Langfuse——排查失败的首选数据源（下一节）。

入口二（本地快速）：harness CLI —— 无 Judge 的 smoke

python -m harness doctor                  # 环境自检
python -m harness run --backend mock      # 跑 categories 业务集，出 JSON + markdown 报告
python -m harness node-run ...            # 单节点执行与回放（ADR 0029）

3. 查错 SOP：从 score 到根因文件（8 分钟）

失败 case 的定位有固定套路（CLAUDE.md"排查与修复流程"），按 Langfuse 富集 JSON 的字段查表：

eval stdout 找到  "LangFuse 写入成功  run=local-YYYYMMDD-HHMMSS"
→ Langfuse UI 按 run name 过滤 → 点开失败 case
→ 顶层 score + judge_comment 锁定差异
→ turns[i] 按字段定位错误层 ↓
哪个字段错了根因大概率在
product_typeapp/nodes/intent_route.py（一级路由）
intent子图 intent.py 的提示词
标的识别错核对传给 Java 的证券原文与后端工具日志（ADR 0025，本地不做标的解析）
place_params 字段漏子图 extract_*.py 提示词
api_result 含"正在处理/请勿重复"后端 dedup（eval 节奏问题，workaround 只准进 langfuse_eval.py，绝不进业务代码）
error 非空看 error.node + error.message（第 03 课的 ErrorInfo）

读 trace 时记住第 05 课的结论：它是累积的（add reducer），多轮 case 的本轮节点在末尾；找"第一个错的节点"，fallback 的 triggered_by: 直接告诉你（第 02 课）。

定位到根因后走第 07 课的 TDD：写复现测试 → RED → 最小修复 → GREEN → 全量回归 → 重跑对应 golden case 确认。三课在这里合流成完整的修 bug 闭环。

4. 节点级 PR 交付标准（4 分钟）

你的第一个 PR 按这张单子自检（出处：.claude/rules/git-workflow.md + docs/training/README.md）：

  1. feature 分支开发（feature/xxx），不动 main
  2. pytest tests/ -v 全绿 + ruff check app/ tests/ 零警告 + mypy app/ 无错
  3. 该节点至少 5 条 golden 全 PASS（这是节点 PR 的"绿"标准——PASS 率，不是行覆盖率）
  4. 改了提示词 → 按 ADR 0001 D5 处置表登记；改了 State → 声明 + 初始化同步
  5. PR 标题/描述中文（feat(swap): ... 前缀保留），含 变更内容/验证/关联 issue 小节
  6. commit 遵循 <type>(<scope>): ...；无硬编码 secret

5. 毕业练习（3 分钟 + 课后）

毕业任务：完整闭环一次

  1. 跑 python -m harness run，打开报告，任选一条非 PASS 的 case（没有就找导师要一条已知错例）
  2. 按第 3 节 SOP 定位到根因文件，写一段"根因分析"（哪个字段错 → 哪个节点 → 为什么）发助教核对
  3. 与导师确认后按 TDD 修复，走完第 4 节的 PR 清单，提交你的第一个 PR

这就是错例修复的日常工作本身——完成即毕业。

6. 小测（毕业考）

自测 · 4 题

1. pytest 全绿但 golden PASS 率跌了，说明什么？

测试测代码正确性（mock LLM），评估测端到端行为（真 LLM）——两套体系正交。改 expected 迁就结果 = 面向测试编程（红线）；Judge 抖动存在但先按 SOP 定位而不是刷分。

2. 失败 case 的 turns 里 intent 错了（product_type 正确），第一站去查哪里？

product_type 对 → 一级路由没问题；intent 是子图内二级意图分类的产出，查子图 intent.py + 它加载的提示词（CLAUDE.md 定位表）。

3. eval 多轮间隔太短撞了后端 dedup（"请勿重复提交"），正确处理是？

这是评估节奏问题，workaround 只准进评估脚本。b 是"掩盖后端真实响应"P0 红线的原型案例（用户会看到伪造订单卡）；c 是往业务代码塞测试专用路径，同样禁止。

4. 节点级 PR 的"绿"标准是什么？

节点 PR 的验收单位是"该节点的 golden PASS"（≥5 条），不是行覆盖率；92.5% 这类整体数字不是单 PR 门槛；数据集层评测门是"PASS 率不低于前值"（ADR 0030 D3）。
