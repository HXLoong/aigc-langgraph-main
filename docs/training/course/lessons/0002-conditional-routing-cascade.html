LangGraph 团队实战课 · 第 02 课

条件路由与 cascade 防御

Dify 的 if-else 节点在这里变成一个 Python 函数 + 一张映射表。本课学会写项目级路由，并理解为什么每个路由的第一行都在检查 error。

编写者：图灵科技预计用时：25 分钟前置：第 01 课小测全对
为什么学这个（对齐任务） Dify 主干工作流里那个 12957 行 YAML 的核心复杂度，一大半在 if-else 分支和连线上。重构成 LangGraph 后，这些分支全部收敛为几个路由函数——读懂它们，你就读懂了整个流程的骨架。而 cascade 防御是本项目 review 必查项（CLAUDE.md 核心原则第 8 条），写错会被打回。

1. 主图一级路由：全项目最重要的 14 行（8 分钟）

打开 app/graph/main.py，这是真实代码（一字未改）：

def _route_after_intent(state: AgentState) -> str:
    """intent_route 节点后的路由。

    优先级：
    1. state['error'] 存在 → fallback（cascade 防御，CLAUDE.md 核心原则第 8 条）
    2. product_type == "unknown" → fallback（unknown 兜底；联合解析目标见 ADR 0031）
    3. 否则按 product_type 选子图
    """
    if state.get("error") is not None:
        return "fallback"
    pt = state.get("product_type", "unknown")
    if pt == "unknown":
        return "fallback"
    return pt

路由函数两条纪律（第 01 课的延伸） ① 同步纯函数：不 await、不调 LLM、不发 HTTP。注意 _route_after_intent 只是"读结论"——真正判断 product_type 的三层策略（正则 → 关键词 → LLM 兜底）在上游 intent_route 节点里做完并写进 state。② 返回的字符串必须是映射表的 key，返回了表外字符串 → 运行时报错。

2. 子图二级路由：一张 dict 看完所有意图分发（7 分钟）

swap 子图按 intent 分发到 5 个真节点 + 1 个兜底，Dify 里要拖 6 条 if-else 分支，这里是一张表：

_INTENT_TO_NODE: dict[str, str] = {
    "place_order_request": "swap_place_order",
    "cancel_order_request": "swap_cancel",
    "confirm_order": "swap_confirm",
    "confirm_cancel_order": "swap_confirm",      # 3 个 confirm 共用一个节点（ADR 0001 D5）
    "confirm_modify_order": "swap_confirm",
    "query_order_status": "swap_query_order",

def _route_after_swap_intent(state: AgentState) -> str:
    """swap.intent 后路由：cascade 防御 + intent 分发。"""
    if has_error(state):
        return "swap_unknown"
    intent = state.get("intent") or "unknown_intent"
    return _INTENT_TO_NODE.get(intent, "swap_unknown")

注意最后一行的 .get(intent, "swap_unknown")——LLM 万一输出了表外的意图，也不会崩，走 swap_unknown 兜底。加一个新意图 = 表里加一行 + 写一个新节点文件，这就是"节点级 PR"的物理基础。

3. cascade 防御：错误只降级、不扩散（7 分钟）

完整链路串起来看：

某节点抛异常
  → @safe_node 捕获，写 state["error"] = ErrorInfo(node=..., message=...)   # 图不崩
  → 下游路由第一行 if state.get("error") → 返回 "fallback"                  # 不再执行业务节点
  → fallback 节点在 trace 里记录 triggered_by:<失败节点名>                 # 可定位
  → render 节点看到 error → 输出"我没完全理解你的意思，能换种说法……"      # 用户侧友好
  → API 层 status="failed" + error message                                  # 调用方可感知

项目提供了两个现成工具：判错函数，以及三个子图共用的意图分发路由（error 优先落本子图的 <product>_unknown）：

def has_error(state: Mapping[str, Any]) -> bool:
    return state.get("error") is not None

def intent_router(intent_to_node: Mapping[str, str], fallback: str):
    def route(state: AgentState) -> str:
        if has_error(state):
            return fallback
        return intent_to_node.get(state.get("intent") or "unknown_intent", fallback)
    return route

fallback 节点本身只做一件事——把"是谁的锅"写进 trace，供 harness 定位：

@safe_node
async def fallback(state: AgentState) -> dict[str, Any]:
    err = state.get("error")
    err_node = err.node if err else "no_error"
    return {"trace": [TraceEntry(node="fallback", decision=f"triggered_by:{err_node}")]}
app/nodes/fallback.py:17-33
Dify 老成员对照 Dify 里节点失败默认重试 N 次后整个工作流失败，想做兜底要在每个分支后挂"代码节点 + try/except"。LangGraph 本身没有这个机制——是我们用 @safe_node + 路由检查自己搭的约定。所以它靠纪律维持：漏写一处检查，错误就会 cascade 到下游节点，产生一堆令人困惑的连环报错。

5. 小测（拿到全对再进第 03 课）

自测 · 4 题

1. 为什么 _route_after_intent 不自己调 LLM 判断 product_type，而是读 state 里的现成字段？

这是项目纪律而非框架强制——判断逻辑（含 LLM）放 intent_route 节点做完写进 state，路由只读结论（.claude/rules/langgraph-patterns.md）。

2. LLM 给 swap 子图输出了一个表外意图 "transfer_money"，会发生什么？

_INTENT_TO_NODE.get(intent, "swap_unknown") 的默认值兜底——注意"表外意图"和"路由函数返回映射表外的 key"是两回事，后者才会报错。

3. cascade 防御的"防御"防的具体是什么？

error 写入后若下游照常执行业务节点，会基于残缺 state 产生一串误导性错误。cascade 防御让流程在第一个失败点就转向 fallback（CLAUDE.md 核心原则第 8 条）。

4. fallback 节点的 trace 里 triggered_by:<节点名> 是为了什么？

失败 case 的 trace 末尾总有 fallback——如果不记录 triggered_by，排查时会误以为问题在 fallback 自己（app/nodes/fallback.py docstring）。
