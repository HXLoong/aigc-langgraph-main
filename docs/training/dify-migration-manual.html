01迁移背景与目标

Dify 在 0→1 阶段完成了 3 类业务流程（互换 / 期权 / 期权平仓）、23 个 LLM 节点和企微对接。迁移不是否定 Dify，而是四类问题在图形化平台内无解：

痛点表现根因
无法严肃测试改提示词后回归靠人工"跑几个 case 感觉一下"没有 SDK 层可被 pytest 驱动，内部节点无法 mock
协作冲突主干工作流 12957 行 YAML，双人同改 merge 不可能整个工作流是单文件，无节点级粒度
观测定位难客户报错只能重放整段对话猜哪步错节点级 trace 是平台版功能
运行时不可控Dify 升级可能倒逼工作流适配运行时所有权在平台

迁移三不变量（对外承诺）：

  1. API 协议不变——POST /v1/workflows/run 与 Dify Workflow Run 协议一致，Java 调用方零改动（ADR 0001 D3）
  2. 提示词资产不变——Dify YAML 中的提示词导出为 app/prompts/**/*.md，占位符 {{#node.var#}} 原样保留
  3. 业务 schema 不变——参数模型与 Java 后端 DTO 1:1，意图枚举逐值对齐（docs/api-contracts/）
一句话定位LangGraph 替换的是运行时，不是业务知识。从外部看，新系统"长得像 Dify"。

03迁移方法论

3.1 Harness-first（ADR 0001）

先建评测台再迁代码：golden case 固化 Dify 行为 → harness 跑 LangGraph 输出与期望 diff → 每迁一个节点立即回归。这保证了"迁移正确性"是可测量的，而不是感觉。

3.2 节点级蓝图 + 节点级 PR

把 Dify 主干拆成节点蓝图（swap / option / option_close / ticker），每个节点一个 .py 文件、一个 PR、≥5 条 golden 作为该 PR 的"绿"标准。节点间无共享可变状态，团队并行迁移互不冲突。

3.3 里程碑

阶段内容状态
M1骨架：主图 + API 兼容层 + State + safe_node + 子图 stub完成
M2主干节点全量迁移（swap/option/close/ticker），mock 后端 PASS ≥ 92.5%完成
M3工程联调闭环：真后端 e2e + Judge 评估 + 错例修 P0/P1 + 业务 sign-off（ADR 0016）M3.3 进行中
DSL v2Dify 侧生产调优后二次对齐：拓扑重构 + 提示词瘦身 + 去 LLM 化（2026-08）进行中（见第 11 章）
M4灰度全量：canary 按群组切流 + shadow 双跑，工具链已就绪待启动

04节点类型迁移对照（核心）

Dify 的每类节点在本仓库的标准做法。写新节点时按这张表对号入座。

4.1 开始节点 / 变量 → ingest + AgentState

Dify start 节点的 inputs（9 个机器人上下文字段）由 ingest 节点解构写入 AgentState（app/graph/state.py）。Dify 的"全局变量命名空间"（{{#节点ID.var#}} 任意引用）变为显式声明的 TypedDict schema——字段不声明则 mypy 拒绝，重命名即全图编译期报错。字段按业务对象聚合（place_params / tickers…），不按节点铺开（ADR 0001 D6）。

4.2 LLM 节点 → 三件套

@safe_node
async def swap_intent(state: AgentState) -> dict:
    prompt = load_prompt("swap", prompt_name)                    # ① 提示词：.md 资产
    llm = get_qwen_thinking().with_structured_output(SwapIntentOutput)  # ② 工厂 ③ 强类型
    result = await llm.ainvoke([("system", prompt.system), ("user", user_message)])
    return {"intent": result.type, "trace": [...]}   # result 是 Pydantic 实例
app/subgraphs/swap/intent.py（模板；全库 20+ LLM 节点同构）

对应关系：Dify 的 prompt_template → load_prompt()；structured_output.schema → Pydantic 模型（意图类小输出 extra="forbid"，参数提取大输出 extra="ignore"）；模型配置 → 工厂函数。解析失败链路：框架自带 1 次重试 → ValidationError → @safe_node 兜底 → fallback。

4.3 if-else 条件分支 → 路由函数 + dict 映射表

def _route_after_swap_intent(state: AgentState) -> str:
    if has_error(state):                              # cascade 防御，永远第一行
        return "swap_unknown"
    return _INTENT_TO_NODE.get(state.get("intent") or "unknown_intent", "swap_unknown")
app/subgraphs/swap/graph.py

纪律：路由是同步纯函数（不 await / 不调 LLM / 不发 HTTP，判断在上游节点做完写进 state）；每个子图必须有 unknown 兜底节点接住表外值。

4.4 代码节点 → 普通函数

Dify 里 YAML 转义的 Python 字符串，迁移后就是节点函数体本身——LangGraph 不区分"代码节点 / LLM 节点"，所有节点都是 async 函数。原代码节点里私拉的 requests 调后端一律改走第 4.5 条。

4.5 HTTP 请求节点 → Protocol Client

三个 Protocol（SwapClient / OptionClient / TickerClient，app/tools/）+ Httpx 实现（认证、tenacity 重试、dry_run 拦截集中在实现层）。ReqVO 与 Java DTO 1:1。节点内禁止直接 httpx.AsyncClient（ADR 0001 D2）。测试用 FakeClient 或 transport 注入 mock HTTP 层。

4.6 工作流嵌套 → Subgraph

g.add_node("swap", build_swap_graph())——子图就是主图的一个节点，与主图共享 AgentState（子图写的字段自动回传，render 统一消费）。三个业务子图同构：intent → 路由表 → 业务节点 + unknown 兜底。

4.7 错误处理 → @safe_node + cascade 防御

Dify"节点失败重试 N 次后整个工作流失败"的语义，替换为：异常被 @safe_node 捕获写 state["error"]（图不崩）→ 下游路由第一行检查 → 跳兜底节点 → render 输出友好话术 → API 返回 status="failed"。这是项目约定而非框架机制，靠纪律维持（CLAUDE.md 核心原则第 8 条）。

4.8 Agent / 工具类工作流 → ticker 解析管线

Dify 的"标的智能化推断和分词工具"迁移为 app/subgraphs/ticker/：业务节点通过 resolve_ticker_full(raw_text) 调用，内部是 DSL v2 的 12 节点管线——候选提取 → 并行 LLM 工具（infer_code / split_keywords / judge_type）→ 确定性合并 → GOATS 检索 + LLM 排序 → winner。注意：它不是主图分支，是业务节点内调用的工具层。早期 ReAct Agent（create_agent）实现已在 DSL v2 重构中被此管线替代。

05状态、多轮与二次确认

5.1 恢复语义

Dify 会话变量 → Checkpointer：每个节点跑完全量 state 快照落库，同 thread_id（固定 = conversation_id，企微会话 ID）下次自动恢复，新输入按 reducer 规则合并——覆盖型字段覆盖、history_messages / trace（Annotated[list, add]）累加。生产 AIOMySQLSaver（lifespan 单例，MySQL 8.0.19 ≤ v < 9.6.0），测试 InMemorySaver。

真实生产事故第 2 轮初始 state 给业务字段设了默认值（如 tickers=[]）→ 覆盖型合并把第 1 轮提取的标的冲掉。初始 state 只放本轮输入字段。

5.2 二次确认：文本两阶段，不用 interrupt（ADR 0021）

原设计（ADR 0006）打算用 interrupt_before 在写+资金类节点前暂停等人工确认，但核查确认该机制从未落地；生产中实际工作的是文本确认路径：机器人回订单卡 →客户回复"确认" → 意图分类到 confirm_* 节点 → 执行写操作。ADR 0021 将其确立为正式机制，interrupt 不做。写节点的人记住：确认是一个普通意图轮次，靠 checkpointer 带上下文，不是图暂停。

06提示词资产管理

6.1 导出管线与目录

python dify/sync.py                                # 拉 Dify 最新 YAML → dify/yaml/
python scripts/export_dify_prompts.py dify/yaml/ /tmp/new-prompts/
diff -r app/prompts/ /tmp/new-prompts/             # 人工审阅，禁止一键覆盖

目录按业务分类：swap/ option/ option_close/ ticker/ router/。陷阱：提示词目录叫 option_close/，代码目录叫 subgraphs/close/，两边不对称。

6.2 纪律（ADR 0001 D5）

重构期内允许定向改写，但每处改写必须登记 D5 处置表；被替代的原始提示词转"非活跃资产"保留（可回滚、可 diff），禁止直接删。全量上线后恢复"只读资产"纪律。

6.3 版本化与来源

A/B 灰度靠文件共存（intent.md / intent_v2.md）+ _versions.yaml 按 conversation_id hash 分流（ADR 0003）；ENABLE_LANGFUSE + use_langfuse_prompts 时优先从 LangFuse 拉取（运行时热更），失败回退本地 .md（ADR 0014）。load_prompt() 有 lru_cache——改 .md 不重启不生效。

6.4 2026-08 瘦身与去 LLM 化

DSL v2 对齐时同步做了两类优化（登记于 D5 处置表 + docs/swap-prompt-slimming-assessment.md）：① swap 长提示词去重瘦身 v2 系列（默认 0 流量，eval 达标才放量）；② 5 个订单号提取节点整体去 LLM 化——原 cancel / query / 三 confirm 节点唯一任务是提取 H-YYYYMMDD-XXXXXXXXXX 订单号，改为确定性正则（swap/order_id.py）：零幻觉、零成本、零延迟。迁移方法论提示：LLM 节点不是目的——凡确定性规则可完成的，迁移时应当降级为代码。

07LLM 供应商层

全部节点统一 DeepSeek-V4-pro（ADR 0020），由 app/llm/clients.py 工厂封装两个 vendor 适配，节点禁止自己 new ChatOpenAI：

  • 关思考模式：DeepSeek 用 {"thinking": {"type": "disabled"}}（会静默忽略 Qwen 的 enable_thinking 参数，不关则长 prompt 延迟 60-180s）
  • structured output 降级：DeepSeek 不支持 response_format=json_schema（400），_ChatLLM 薄层统一降级为 function_calling，全库 43 处调用零改动

工厂保留 standard / thinking / structured / complex / vl 五个函数名以兼容 import 路径；vendor 由 .env 切换（qwen_ 前缀是历史命名）。

08API 兼容层

app/api/routes.py 完整模拟 Dify Workflow Run 协议：请求 {inputs, response_mode: "blocking", user}；响应 {workflow_run_id, task_id, data: {status, outputs, error, elapsed_time, ...}}。user 字段即 conversation_id，直接作 thread_id。节点失败时图正常走完，HTTP 仍 200、data.status="failed" + 可读 error——与 Dify 失败形态对齐，Java 侧（StockBotMessageServiceImpl 写死 blocking）零改动。

09质量保障体系

迁移最大的收益项，两条独立防线：

测试（代码对不对）评估（机器人答得对不对）
手段pytest 三层金字塔（模型/路由单测 → 节点/子图 → e2e），841 passed，mock LLM + FakeClientgolden 350+ 条跑真 LLM：harness run/diff（快速 smoke）+ langfuse_eval.py（DeepSeek Judge，M3 主用）
数据—三桶：B 业务方种子（≥90%）/ C LLM 对抗改写（≥80%）/ D 客户真实输入（累积）
查错pytest --lf / traceLangfuse 富集 JSON 按字段定位：product_type→intent_route、intent→子图提示词、error→error.node

纪律：TDD 强制（先 RED 再 GREEN）；新节点/意图必须同步 golden ≥5 条；mock 必须 patch 使用点（tests/CLAUDE.md 头号陷阱）。

10可观测与上线策略

  • 观测：LangFuse self-hosted（infra/langfuse/，per-node LLM trace 自动注入）+ Prometheus /metrics（节点成功率/耗时由 @safe_node 埋点）+ trace 字段落 MySQL
  • 灰度：按群组 canary 切流（canary_status.py / rollback_canary.sh 一键回切）+ shadow 双跑对比（shadow_compare.py，含 DRY_RUN_BACKEND 写拦截）+ Grafana 面板模板 + on-call runbook
  • 提示词上线：LangFuse Prompt 晋升工具（F4.6），线上热更不发版
