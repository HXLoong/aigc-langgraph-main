# ADR 0017 · M4 金丝雀退出门量化指标

- 状态：已采纳
- 日期：2026-05-12
- 起源：grill-with-docs（docs/m3-m4-roadmap.md F4.7）
- 作者：图灵科技 + Tony

## 上下文

M4 金丝雀阶段（路线图阶段 4）走完 100% 流量切换后，需要一个**明确的退出门**来判定"是否可以下线 Dify"。

路线图原文只写了"100% 流量稳定 7 天无 P0；业务方书面同意 Dify 下线"——两个模糊点：

- "无 P0" 没有量化标准。一次 cascade fail 算 P0 吗？回复延迟从 3s 涨到 8s 算 P0 吗？
- "书面同意" 形式不明。邮件？合同？企微截图？

不补这两个空，团队会在金丝雀末期反复扯皮"算不算稳定了"，业务方也会因为"我没说同意"而无限期不下线 Dify。

## 决策

阶段 4 退出门用以下**量化阈值**判定：

### 系统层指标（监控埋点自动测量）

| 指标 | 阈值 | 测量方式 |
|---|---|---|
| HTTP 5xx 率 | < 0.1% | 7 天总请求数中 5xx 响应占比 |
| Cascade fail 率 | < 1% | LangFuse trace 中 fallback render 节点触发次数 / 总请求数 |
| P95 回复延迟 | ≤ M2 baseline × 1.5 | 监控埋点上报的 P95 值 |

### 业务层指标（业务方人工标注）

| 指标 | 阈值 | 测量方式 |
|---|---|---|
| 业务方反馈的"严重错例" | ≤ 5 次（7 天内累计） | 企微群反馈或周报反馈的标的错/参数错/意图大类错 |

### 书面同意形式

**邮件回复**："收到 LangGraph 上线运行 7 天报告，同意 Dify 工作流下线" + 业务方负责人姓名/职位。

- 不接受口头/电话/微信文字（无法追溯）
- 不需要走合同 amendment（太重，拖项目）

## 阈值取值理由

### 为什么 5xx < 0.1%

5xx 是服务器崩溃，应近似零。0.1% 是万分之一，给边界情况（瞬时网络抖动、上游 timeout 触发的 503 等）留容差。再松（如 1%）就是带病上线。

### 为什么 Cascade fail < 1%

M2 总失败率 7.5%，但其中大部分是意图识别偏差（非 cascade）。真正的 cascade fail（节点抛异常 → fallback 路由触发）远低于此。1% 是用户能感知但不至于"觉得 AI 坏了"的临界值。

### 为什么 P95 而非平均延迟

金融业务方耐心有限——平均 3s 但 P95 12s 的体验**远差于**平均 4.5s 但 P95 6s 的体验。Chat UX 由尾部延迟决定。用 P95 强约束更贴近真实感受。

### 为什么 M2 baseline × 1.5

真后端调用必然引入网络往返（vs mock 的内存调用），1.5 倍是给真后端 + LangFuse 上报 + checkpoint 写入留预算。再松（如 2 倍）就是放任性能退化。

### 为什么严重错例 ≤ 5 次（而非 0 次）

7 天 × 估计每天 100-200 条真实流量 = 700-1400 条。5 次 ≈ 0.5%，业务方仍能接受，且不会因为偶发噪音（单条歧义输入）永远卡门。0 次过严，会出现"业务方挑刺、永远不签字"的扯皮风险。

## 替代方案

### 不用量化指标，只看"业务方主观满意"

放弃：业务方会用主观感受无限期拖延签字。金融客户的风险偏好天然保守，没有数字标尺就会反复挑刺。

### 更严的阈值（5xx = 0、Cascade = 0、错例 = 0）

放弃：100% 完美阈值不现实，会让金丝雀末期陷入"修最后一个 bug → 出现新 bug" 的死循环，永远到不了退出门。

### 更松的阈值（5xx < 1%、错例 ≤ 20）

放弃：金融场景容错低，5xx 1% = 每百条 1 次崩溃，业务方会失去信任。

## 后果

### 正面

- 团队和业务方在金丝雀末期有共同的判定语言
- 退出门可被监控仪表盘自动校验（除业务方反馈外）
- 阶段 5 全量上线起点清晰

### 负面

- 监控埋点必须在阶段 1 子线 1C（C1.5-C1.8）完成时**就要支持这些指标的实时计算**，否则金丝雀末期才发现监控不到位
- 业务方"严重错例"标准需要在阶段 3 sign-off 前与业务方对齐定义（标的错/参数错/意图大类错——而非"AI 不够聪明"这种主观感受）

### 后续行动

- C1.5 任务的埋点必须**包含**：5xx 率、cascade fail 率、P95 延迟三项实时计算
- 阶段 3 业务方培训（E3.6）必须包含**严重错例标准对齐**议题
- F4.7 的报告模板按本 ADR 阈值表格输出
