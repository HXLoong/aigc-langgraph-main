# F4.0 On-Call 应急回切预演剧本

> **版本**: v0.1 草稿（2026-05-12 by 图灵科技工程团队）
> **状态**: 待 Tony walkthrough 验证 → 反馈修订 → v1.0
> **场景**: F4 灰度上线前最后一轮"全员可演练"的应急流程验证
> **关联**: [on-call-runbook.md](../../on-call-runbook.md) 是原则手册；本文档是**可执行剧本**

---

## 1. 目标与通过标准

让 **Tony + 客户企微管理员 + on-call 工程师**三方走完一轮 P0 应急回切，验证 F4 6 件套工具能在**真实压力**下串起来。

| 通过标准 | 量化 |
|---|---|
| 全流程从"故障感知"到"服务侧回切完成" | ≤ 15 分钟 |
| 6 件套工具按预期输出 | 全部 ✅ |
| audit log 记录完整可复盘 | 含时间/原因/操作人/baseline |
| 三方沟通链路无堵塞 | 告警群 → Tony → 企微管理员均 ≤ 3 分钟响应 |
| 演练完恢复到原状 | .env 还原 + 服务正常 + 业务方收到完整通知 |

未达标的演练 = **重做**。F4.0 没过门，F4.2 不切流。

## 4. 演练剧本（约 30 分钟）

### Scene 1 · 基线确认（演练前 5 分钟）

**目的**：演练开始前，6 件套工具基线是绿的，否则演练数据无意义。

#### 一键 smoke（推荐）

```bash
bash scripts/drill_smoke.sh
# exit=0 → 6 项 check 全绿，可进 Scene 2
# exit=1 → 有 ❌，输出末尾列出失败项；修复后重跑
# exit=2 → 参数错 / 环境异常
```

`drill_smoke.sh` 把以下手动步骤打包成 6 个自动 check：工具存在 / 语法可加载 / `/ready` 200 / metrics_snapshot 输出齐全 / canary_status 状态正常 / deploy step 2+9。加 `--json` 可机器解析。

> **想看手动版**或上述 smoke 失败需要逐项 debug 时，继续看下面的分步命令。

#### 分步命令（debug 用）

```bash
# 跑 deploy 脚本的 step 2+9（不实际部署，只校验 .env 和健康检查）
bash scripts/deploy-customer.sh --only 2
bash scripts/deploy-customer.sh --only 9
```

**预期**：
- step 2 输出 `F4 金丝雀启用，白名单群数 = 1`
- step 9 输出 `GET /ready 200（4 个上游全绿）`

```bash
python scripts/metrics_snapshot.py
```

**预期**：
- 节点级表所有错误率 = 0
- LLM 失败率 < 1%
- `is_canary=true`: 有计数（演练群有过流量），`is_canary=false`: 0
- 健康检查 4 个 target 全 ✅

```bash
python scripts/canary_status.py
echo "exit=$?"  # is_breach=true → 1，否则 0
```

**预期**：退出码 `0`，状态 `白名单 1 群`。

**通过条件**：3 条命令全部如上输出。任何一条不符 → **本演练取消**，先修基线。

---

### Scene 2 · 故障注入（T = 0）

**目的**：制造一个可控 P0 信号，看告警链路是否打通。

**选 1 个故障注入方式**（推荐①，影响小）：

#### ① Java 后端不可达（推荐）

故障注入员操作：
```bash
# 临时把 OTC_API_BASE_URL 改成不通的 host（演练专用）
ENV_BACKUP=$(date +%s)
cp .env .env.drill-backup-${ENV_BACKUP}
sed -i.bak 's|^OTC_API_BASE_URL=.*|OTC_API_BASE_URL=http://192.0.2.1:8080|' .env
# 重启服务（演练专用，**生产严禁**）
sudo systemctl restart otc-agent
```

`192.0.2.1` 是 TEST-NET-1（RFC 5737）保留段，**任何环境都不会真通**。

#### ② LLM 模型名错误

```bash
sed -i.bak 's|^QWEN_MODEL_STANDARD=.*|QWEN_MODEL_STANDARD=nonexistent-model|' .env
sudo systemctl restart otc-agent
```

**注入后 30 秒内**告警链路应触发：
- `/ready` 返回 503（java_backend fail 或 llm fail）
- Grafana 大屏 `健康检查` 段对应 target 飘红
- `alerts.py` 触发 P0 告警（推送到告警群——本演练阶段允许人工脚本模拟）

---

### Scene 3 · 告警感知（T+0 ~ T+2）

on-call 工程师拿到告警后**立即**：

```bash
# 一键快照保留现场（事故复盘必须）
python scripts/metrics_snapshot.py > /tmp/drill-snapshot-pre-rollback.txt
```

**核心判定**（≤ 2 分钟内说出三件事）：
1. 是哪一类故障？（Java 后端 / LLM / 节点）
2. 是否达到 P0 标准？（持续多久、影响多少流量）
3. 决定回切还是先排查？

**演练通过条件**：on-call 在 2 分钟内做出"立即回切"决策（演练默认 P0，不允许犹豫）。

---

### Scene 4 · 服务侧回切（T+2 ~ T+7）· **核心 Scene**

#### 4.1 启动 rollback 脚本

```bash
bash scripts/rollback_canary.sh \
    --reason "F4.0 演练 · Java 后端故障注入" \
    --wait-seconds 30
```

**关键交互点**（演练观察 on-call 操作流畅度）：

| 步 | 脚本输出 | on-call 动作 |
|---|---|---|
| Step 1 | `确认要执行 F4 应急回切吗？ [y/N]` | 回 `y` |
| Step 2 | `已备份 → .env.rollback-20260512-...` | 记下文件名 |
| Step 3 | `baseline · is_canary=true: N` | （演练员对照 metrics_snapshot 验证 N 是否一致） |
| Step 4 | `请企微管理员现在执行...` | **立即电话/企微通知客户企微管理员**（同步操作 4.2） |
| Step 4 | 等 30s 后取第二次计数 | 验证 Δ ≤ 5 |
| Step 5 | `CANARY_ROOM_IDS 已清空` | （演练员检查 .env：原值在注释行，新行空） |
| Step 6 | `audit log 追加` | 记下 .rollback-audit.log 路径 |

#### 4.2 Webhook 切换（企微管理员侧，与 4.1 并行）

企微管理员收到通知后：
1. 登录企微管理后台
2. 进入 应用管理 → 自建应用 → otc-agent 机器人
3. 把 Webhook URL 从 `https://<langgraph-host>/v1/workflows/run` 改回 `https://<dify-host>/v1/workflows/run`
4. 保存

**通过条件**：从 on-call 发起通知 → 企微管理员完成切换 ≤ 3 分钟。

---

### Scene 5 · 验证回切完成（T+7 ~ T+10）

on-call 跑：

```bash
python scripts/canary_status.py
echo "exit=$?"  # is_breach=true → 1，否则 0
```

**预期**：退出码 `0`，状态 `未启用（金丝雀关）`（因为 CANARY_ROOM_IDS 已清空）。

```bash
python scripts/metrics_snapshot.py > /tmp/drill-snapshot-post-rollback.txt
diff /tmp/drill-snapshot-pre-rollback.txt /tmp/drill-snapshot-post-rollback.txt
```

**关键观察**：
- `is_canary=true` 段在演练 5 分钟内增量应 ≤ 5（演练群已切回 Dify，不再有新流量）
- 健康检查段错误状态依然存在（**故障还没修，回切只是把客户隔离了**）

打开 Grafana：
- `金丝雀流量占比` 应快速下降到 0
- `is_canary=false · 1h` 仍是 0（白名单只有演练群且已切走，不会有误切）

**通过条件**：所有验证项符合预期。

---

### Scene 6 · 演练后清理与恢复（T+10 ~ T+25）

#### 6.1 修复故障注入

```bash
# 还原 .env
cp ".env.drill-backup-${ENV_BACKUP}" .env
sudo systemctl restart otc-agent
```

#### 6.2 验证服务恢复

```bash
curl -fsS http://localhost:8000/ready
```

**预期**：HTTP 200，`status: ok`，4 个 target 全绿。

#### 6.3 切回 LangGraph（演练完整闭环）

> **遵循 on-call-runbook §7.4 回归流程**：演练当天不切回生产，但演练群可立即切回——这本身也是演练的一部分。

企微管理员：把演练群的 Webhook 从 Dify 改回 LangGraph。

on-call：
```bash
# 重新启用演练群金丝雀
echo "CANARY_ROOM_IDS=r-drill-{date}" >> .env  # 注意：rollback 脚本已注释原行，这里追加新行；演练完成后清理 .env
sudo systemctl restart otc-agent
python scripts/canary_status.py
```

**预期**：状态恢复"白名单 1 群"。

#### 6.4 在告警群通报

> **"F4.0 演练完成 · 用时 XX 分钟 · 全部通过 / 发现问题 N 项（详见 review）"**

## 7. 演练失败的兜底

如果演练中任何 Scene 卡壳 ≥ 2 分钟未恢复：

1. 立即在告警群通报 **"演练异常中止"**
2. 故障注入员**立即**还原 .env 并重启
3. 业务方群通报"系统恢复，演练异常但已无生产影响"
4. 当日故障复盘会议（小时级）
5. 修复后**重新演练**——F4.2 切流推迟

> **绝不允许带着演练失败硬上生产**。
