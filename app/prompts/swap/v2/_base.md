placeOrderQuantity(委托数量,数字,单位:股):

placeOrderQuantityTotal(总量,数字,单位:股):

- **关键字段**:表示要交易的总量,是所有账户数量的总和
- **适用场景**:仅当算法类型为POV时需要填写,配合placeOrderTotalPovPercent使用
- **提取规则**:
  * 确保为整数格式,去除"股"等单位
  * 所有订单对象必须使用相同的总量值
  * 当用户文本中明确提到"总共32000股"等表述时,可从文本提取
- 非POV算法或未提供总量则为null。

placeOrderTotalPovPercent(总单POV比例,数字):

- **新增字段**:表示整个总单的POV比例,用于后续按数量占比分配给各交易对手
- **关键说明**:此字段与placeOrderPovPercent的区别:
  * placeOrderTotalPovPercent:总单的POV比例(如3%)
  * placeOrderPovPercent:每个交易对手实际分配的POV比例,由后处理脚本自动计算
- **适用场景**:仅当算法类型为POV且**同时存在placeOrderQuantityTotal(总量)**时才需要填写
- **【极其重要】前置条件**:此字段**必须且只能**在总单场景下填写。判断总单场景的标准:**当前订单或history_query_str中的订单存在placeOrderQuantityTotal(不为null)**。如果不存在总量,此字段**必须为null**,POV比例应设置到placeOrderPovPercent
- **识别规则**(仅在确认为总单场景后才适用):
  * 识别"跟量X%"格式,如"跟量3%"placeOrderTotalPovPercent = 3
  * 识别"POV X%"格式,如"POV 15%"placeOrderTotalPovPercent = 15
  * 去除"%"符号,保留数值
- **重要**:所有订单对象必须使用相同的总单POV比例值
- **后处理逻辑**:当placeOrderQuantityTotal和placeOrderTotalPovPercent都存在时,后处理脚本会自动计算每个交易对手的placeOrderPovPercent:
  * placeOrderPovPercent = placeOrderTotalPovPercent × (placeOrderQuantity / placeOrderQuantityTotal)
- 当用户文本中明确提到总单POV比例时可提取
- 未识别到总单POV比例则为null。

placeOrderOrderDirection(委托方向,字符串,对应GoatsOrderDirection枚举):

- **枚举值只有4个**: BUY、SELL、SHORT_OPEN、SHORT_CLOSE,**绝对禁止**输出任何其他值(如"BUY_CLOSE"、"SELL_OPEN"等都是无效值!)
- **【极其重要】强制分步匹配流程**(必须按步骤顺序执行,**绝对禁止跳过步骤1直接匹配步骤2**):

  **步骤1(最先检查): 检查是否包含4字方向词**
  * 输入包含"买入开仓" → 输出"BUY",结束
  * 输入包含"买入平仓" → 输出"SHORT_CLOSE",结束 (**买入平仓=平空,不是BUY!**)
  * 输入包含"卖出开仓" → 输出"SHORT_OPEN",结束 (**卖出开仓=卖空,不是SELL!**)
  * 输入包含"卖出平仓" → 输出"SELL",结束 (**卖出平仓=卖出,不是SHORT_CLOSE!**)
  * 如果步骤1匹配到任何一个 → **直接输出对应值,不再执行步骤2和步骤3**

  **步骤2(仅当步骤1未匹配时): 检查2字方向词**
  * 输入包含"买入" → 输出"BUY",结束
  * 输入包含"卖出" → 输出"SELL",结束
  * 输入包含"卖空" → 输出"SHORT_OPEN",结束 (**卖空≠卖出,不是SELL!**)
  * 输入包含"平空" → 输出"SHORT_CLOSE",结束
  * 输入包含"做多" → 输出"BUY",结束
  * 输入包含"做空" → 输出"SHORT_OPEN",结束

  **步骤3(仅当步骤1和2都未匹配时): 检查1字方向词**
  * 输入包含"多" → 输出"BUY",结束
  * 输入包含"空" → 输出"SHORT_OPEN",结束

- **【极其重要】为什么必须先检查步骤1**:
  * "卖出开仓"包含子串"卖出",如果跳过步骤1直接匹配步骤2,会错误匹配"卖出"→SELL
  * "买入平仓"包含子串"买入",如果跳过步骤1直接匹配步骤2,会错误匹配"买入"→BUY
  * "卖出平仓"虽然最终也映射为"SELL",但它仍是**完整方向术语**,必须优先按步骤1整体识别,**禁止拆词后碰巧命中**
  * **必须先用步骤1的4字词完整匹配,排除后才能进入步骤2**
- **【极其重要】开平仓是完整术语,绝对禁止按字面拆分**:
  * "买入平仓"、"卖出开仓"、"卖出平仓"、"买入开仓"各自是一个**不可拆分的完整方向术语**
  * **绝对禁止**拆成"买入"+"平仓"或"卖出"+"开仓"再分别理解
  * **绝对禁止**自行拼造枚举值(如"BUY_CLOSE"、"SELL_OPEN"等)
- **【严重错误示例】**(绝对禁止):
  * 用户说"卖出开仓" → 输出"SELL"(严重错误!应为"SHORT_OPEN")
  * 用户说"卖出平仓" → 输出"SHORT_CLOSE"(严重错误!应为"SELL")
  * 用户说"卖空" → 输出"SELL"(严重错误!应为"SHORT_OPEN")
  * 用户说"买入平仓" → 输出"BUY"(严重错误!应为"SHORT_CLOSE")
  * 用户说"买入平仓" → 输出"BUY_CLOSE"(严重错误!无此枚举值!)
- 从swap_query中提取。
- **【极其重要】委托方向位置无关规则**:
  * 委托方向关键词可以出现在输入文本的**任何位置**(开头、中间、末尾),都必须正确识别
  * **绝对禁止**因为方向词出现在末尾就截断匹配(如"买入平仓"在末尾时只匹配到"买入")
  * **强制要求**: 提取方向时,必须先**扫描完整输入文本**找出所有方向候选词,然后对每个候选词执行分步匹配流程
  * **正确示例**(方向词在不同位置,结果必须一致):
    - "0700.HK 100股 限价50 买入平仓" → "SHORT_CLOSE"(末尾,正确)
    - "买入平仓 0700.HK 100股 限价50" → "SHORT_CLOSE"(开头,正确)
    - "0700.HK 买入平仓 100股 限价50" → "SHORT_CLOSE"(中间,正确)
  * **严重错误示例**:
    - "0700.HK 100股 限价50 买入平仓" → "BUY"(严重错误!因为在末尾就只匹配了"买入",应为"SHORT_CLOSE")
- **绝对禁止**:为方向字段设置任何默认值(如默认"SELL"),用户未明确提供则必须为null。
- 未提供则为null。

- **"均价"作为TWAP别名自动识别规则**:当用户使用"均价"表达时,自动识别为TWAP:

  * **禁止**: "均价"绝不得映射为VWAP
- 其他算法类型(VWAP、ICEBERG、SNIPER)必须明确指定,不自动推断。

  - "pov比例改为25%"  placeOrderPovPercent = 25 (普通场景,默认设置placeOrderPovPercent)

  - "pov 11:25-11:30"  placeOrderPovPercent = null(11:25是时间,不是比例)

  - 总单场景(有placeOrderQuantityTotal)补充"20%"  placeOrderTotalPovPercent = 20, placeOrderPovPercent = null
  - **【严重错误】**: 非总单场景下"pov比例改为25%"  placeOrderTotalPovPercent = 25(错误!应设置placeOrderPovPercent = 25)
- 未提供则为null。

- 未识别到相对时间表达式则为null。

placeOrderStartTime(算法开始时间,字符串,格式HH:MM):
placeOrderEndTime(算法结束时间,字符串,格式HH:MM):

- 当用户提供算法时间窗时解析;TWAP通常需要时间窗(必需)。

- **【重要】时间格式规范化要求**:
  * **强制格式**: 必须严格按照HH:MM格式输出(小时和分钟都必须是2位数)
  * **补零规则**:
    - 单位数小时必须补0: "9:00" → "09:00", "9:30" → "09:30"
    - 单位数分钟必须补0: "15:5" → "15:05", "9:5" → "09:05"
  * **错误示例**: "9:00", "9:30", "15:5" (缺少前导零)
  * **正确示例**: "09:00", "09:30", "15:05" (符合HH:MM格式)

- **格式化处理流程**:
  1. 从用户输入中提取时间(如"9:00", "9:30", "14:5")
  2. 检查小时部分是否为单位数,是则补0(9 → 09)
  3. 检查分钟部分是否为单位数,是则补0(5 → 05)
  4. 输出规范化后的时间("09:00", "09:30", "14:05")
  * **严禁12/24小时制推断**:用户输入"5:00"只能补零为"05:00",绝不能推断为"17:00";用户输入"1:00"只能补零为"01:00",绝不能推断为"13:00"。只做格式补零,不做语义纠正。

- **【最高优先级】时间窗提取流程**:
  1. 先按原文切分时间窗左右两侧(如"9:00-5:00"切为左侧"9:00"、右侧"5:00")
  2. 左侧时间只做补零后写入placeOrderStartTime
  3. 右侧时间只做补零后写入placeOrderEndTime
  4. **绝不交换左右两侧、绝不改写数值、绝不补"下午"语义**
  5. 即使右侧时间早于左侧时间,也必须保持原文语义: "9:00-5:00" → placeOrderStartTime="09:00", placeOrderEndTime="05:00"
  6. 时间顺序是否合法由下游校验负责,**不属于本节点**

- **两种时间表达方式**:
  * **绝对时间**:使用具体时间点(如"9:30-10:30"),填写此字段并规范化为HH:MM格式
  * **相对时间**:使用相对时长(如"TWAP十分钟"),填写placeOrderRelativeTimeMinutes字段,此字段为null

- 支持"HH:MM-HH:MM""HH:MM到HH:MM"格式:
  - 输入: "9:30-10:30" → 输出: placeOrderStartTime="09:30", placeOrderEndTime="10:30"
  - 输入: "14:00到15:30" → 输出: placeOrderStartTime="14:00", placeOrderEndTime="15:30"
  - 输入: "9:00-15:00" → 输出: placeOrderStartTime="09:00", placeOrderEndTime="15:00"

- **重要**:时间窗中的数字只能解析为时间,不能解析为其他参数(如POV比例)。

- **示例**(注意时间格式规范化):
  - "pov 11:25-11:30" → placeOrderStartTime="11:25", placeOrderEndTime="11:30"
  - "POV25% 14:00-15:00" → placeOrderStartTime="14:00", placeOrderEndTime="15:00"
  - "9:00-15:00" → placeOrderStartTime="09:00", placeOrderEndTime="15:00" (补零!)
  - "9:00-5:00" → placeOrderStartTime="09:00", placeOrderEndTime="05:00" (只补零,不做下午推断!)
  - ❌ 错误示例: "9:00-5:00" → placeOrderStartTime="09:00", placeOrderEndTime="17:00" (错误!这是语义纠正,不是格式化)
  - "9:30-10:30" → placeOrderStartTime="09:30", placeOrderEndTime="10:30" (补零!)
  - "TWAP十分钟" → placeOrderStartTime=null, placeOrderEndTime=null, placeOrderRelativeTimeMinutes=10

- 特殊短语映射(已规范化为HH:MM格式):
  - "上午开盘后" → "09:30"
  - "下午开盘后" → "13:00"

- **【即时下单规则】**:当用户使用口语化表达"立即执行"语义时,使用now_date_time加1分钟作为placeOrderStartTime
  * **触发词**:"现在"、"马上"、"即刻"、"立刻"、"立即"、"即时"、"赶紧"、"赶快"等表达"立即执行"的口语词汇
  * **计算规则**:将now_date_time(HH:mm格式)的分钟数加1,结果仍以HH:MM格式输出
    - 示例:now_date_time="14:32" → placeOrderStartTime="14:33"
    - 示例:now_date_time="09:07" → placeOrderStartTime="09:08"
    - 跨小时:now_date_time="13:59" → placeOrderStartTime="14:00"
    - 跨零点:now_date_time="23:59" → placeOrderStartTime="00:00"
  * **placeOrderEndTime**:用户若未明确提供结束时间,则保持null
  * **优先级**:此规则低于用户明确指定的绝对时间(如"9:30-10:30"),高于无时间输入的默认null
  * **禁止误触发**:仅当用户的时间表达使用了上述触发词,且未提供任何具体时间点时才启用此规则

- 若仅给出开始/结束之一,则仅填对应字段(记得补零),另一字段为null。

placeOrderShortname(交易对手简称/交易账号,字符串):

- **【最高优先级】订单列表JSON提取规则**:
  * **检测JSON格式**:如果swap_query包含JSON数组格式的订单列表(以`[{`开头包含`placeOrderShortname`字段)
  * **优先使用JSON数据**:必须从JSON数组中的`placeOrderShortname`字段提取交易对手名称
  * **JSON优先级最高**:JSON中的值是经过预处理的准确值
  * **防止幻觉的关键**:JSON数据可以避免解析错误
  * **提取示例**: swap_query包含`[{"placeOrderShortname":"账户A",...},{"placeOrderShortname":"账户B",...}]`
    - 第1个订单的placeOrderShortname必须从JSON[0].placeOrderShortname提取,即"账户A"
    - 第2个订单的placeOrderShortname必须从JSON[1].placeOrderShortname提取,即"账户B"
    - **绝对禁止**重新解析(可能不准确)

- **【次优先级】基于shortname_list辅助匹配规则**(当swap_query不包含JSON订单列表时使用):
  * **如果提供了shortname_list(非空)**:将swap_query中的文本与shortname_list中的名称进行匹配
    - 扫描swap_query,查找是否包含shortname_list中任意一个交易对手名称
    - 如果匹配到,直接使用shortname_list中的**完整名称**作为placeOrderShortname(确保字符精确)
    - 匹配时应支持模糊位置(交易对手名称可能出现在输入的任意位置)
    - 如果匹配到多个,按在swap_query中出现的顺序对应到各订单
  * **如果shortname_list为空或未匹配到**:回退到传统提取规则
  * **传统提取规则**:
    - **必须从swap_query原始输入逐字符提取**,绝不使用提示词示例中的任何账户名
    - **每一行都重新提取**:处理第N行时,必须从swap_query第N行提取,不得记忆前面行的结果或示例
    - **验证提取结果**:提取后必须确认该账户名在swap_query中真实存在
    - **绝对禁止**:输出任何不在swap_query中的账户名（即使它在提示词示例中出现过）

- **重要前置步骤**:在识别交易对手之前,必须先执行【机器人名称过滤规则】,从输入内容中移除所有机器人名称
- 识别模式:
  - "交易对手:XXXX"提取"XXXX"(冒号后完整内容,最优先识别);
  - "交易对手: XXXX"提取"XXXX"(冒号后可能有空格,提取时去除冒号和紧跟的空格,但**保留XXXX内部的所有空格**);
  - "账号XXXX""交易账号XXXX""交易账户XXXX""用账号XXXX下单"等,提取紧邻数字/数字+中文组合;
  - **【极其重要】选项格式识别规则**(当用户引用机器人的选项消息时):
    * **触发场景**:当quote_content包含选项格式(如"A.选项1"、"B.选项2"、"D.23"),且用户回复字母选择或序号选择时
      - 字母选择:如"D"、"d"、"A"、"a"
      - 序号选择:如"第一个"、"第1个"、"第一项"、"第4个"、"第四项"
    * **处理规则**:必须提取字母选项后面的真实值,而不是字母本身或"字母.值"组合
      - **选项前缀剥离规则**:`A.`、`B.`、`C.`、`D.` 等仅是选项标识符,**绝对不属于交易对手短名本身**
      - 无论用户回复字母选择(如`B`)还是序号选择(如`第二个`、`第2个`),都必须先定位到对应选项,再**剥离开头的`字母.`前缀**后输出真实交易对手值
      - 例如:`B.11125测试短名(张天琪专用)` 的真实交易对手是 `11125测试短名(张天琪专用)`,**不是** `B.11125测试短名(张天琪专用)`
      - 如果选项格式为 `B. 11125测试短名(张天琪专用)`,也只去掉前缀 `B.` 和其后紧跟的空格,保留后续真实值原文
    * **大小写规则**:选项字母匹配时必须**大小写不敏感**
      - quote_content里的选项通常是大写"A.""B.""C.""D."
      - 用户回复可以是大写或小写,如"A"与"a"、"D"与"d"必须视为同一个选项
      - **仅选项字母允许大小写不敏感匹配**;提取出的真实交易对手内容仍必须按quote_content中的原文逐字符输出
      - **字母有效性校验**:用户回复的小写或大写字母,只能匹配quote_content中**真实存在**的同一字母选项;如果不存在对应字母选项,则视为未选中任何交易对手
      - 例如:quote_content存在`F.账户F`时,用户回复`f`必须匹配到`F.账户F`;如果quote_content只有`A`到`E`,则用户回复`f/F`无效,`placeOrderShortname`必须保持`null`
    * **序号规则**:当用户回复"第x个""第x项""第x条""第x位"时,必须按quote_content中选项的**显示顺序**映射到对应字母选项
      - **序号从1开始计数(1-based)**:"第1个"就是第1个真实选项,绝对不是第0个;不允许0-based、就近匹配或模糊猜测
      - **【最高优先级门禁 — 序号越界校验,查映射表之前必须先执行,不可跳过】**:
        处理"第x个"时,必须严格按以下顺序执行,禁止跳步:
        ```
        步骤1: 扫描quote_content,统计形如[A-Z].的有效选项数 → N = ?
        步骤2: 从用户输入提取序号 → x = ?
        步骤3: 判断 x 是否在 [1, N] 范围内?
                若 x < 1 或 x > N → placeOrderShortname = null,立即终止,禁止查表
                若 1 ≤ x ≤ N → 通过门禁,允许继续查下方映射表
        ```
        ❌ x > N 时把 x 截断为 N（如"第6个"→第5个）—— 严重错误
        ❌ x > N 时选最后一个有效选项 —— 严重错误
        ❌ x > N 时用"最接近"逻辑猜测 —— 严重错误
        ❌ 跳过本校验直接查映射表 —— 严重错误
      - **默认顺序映射表**(⚠️ 仅当上方门禁校验通过、确认 1 ≤ x ≤ N 后才可查询,越界时禁止使用):
        1 ↔ A
        2 ↔ B
        3 ↔ C
        4 ↔ D
        5 ↔ E
        6 ↔ F
        7 ↔ G
        8 ↔ H
        9 ↔ I
        10 ↔ J
        ⚠️ 再次强调:以上映射仅当 x ≤ quote_content实际选项数 N 时才可使用;x > N 时必须直接 placeOrderShortname = null,不得查表。
      - 中文数字与阿拉伯数字都必须支持:
        * "第一个""第一项""第1个""第1项" → 第1个选项 → A
        * "第二个""第2个" → 第2个选项 → B
        * "第三个""第3个" → 第3个选项 → C
        * "第四个""第4个" → 第4个选项 → D
      - 必须先统计quote_content中**真实存在**的有效选项数量,只有落在`1..选项总数`范围内的序号才有效
      - 如果quote_content中只有4个选项,则"第一个"到"第四个"有效,不得凭空继续映射不存在的第5个选项
      - 如果quote_content中只有5个选项,则"第6个""第六个""第6项"全部无效,`placeOrderShortname`必须为`null`
      - **绝对禁止**:序号越界时向前兜底到最后一个选项、按最接近序号猜测、或把"第6个"错误映射成第5个选项
      - 如果quote_content中的选项字母不是连续的,则**优先按quote_content中真实出现的顺序位置映射**,不要死记字母
    * **识别步骤**:
      1. 检查quote_content是否包含选项格式(正则可按大小写不敏感理解,如:`[A-Za-z]\..+`)
      2. 检查用户raw_content是否为单个字母、多个字母,或序号表达(如"D"、"d"、"A"、"a"、"B,D"、"b,d"、"第一个"、"第1个"、"第四项")
      3. 如果是字母回复,先验证该字母对应的选项是否在quote_content中真实存在;存在才匹配,不存在则视为无效选择
      4. 如果是序号回复:先统计quote_content中的实际选项总数N;**立即判断x是否在范围内**:若x > N → 直接输出`placeOrderShortname: null`,终止流程,**不得继续查映射表**;若1 ≤ x ≤ N,才按顺序映射到对应选项
      5. 如果字母或序号无效/越界,`placeOrderShortname`必须保持`null`,不得回填任何现有选项,**不得向前兜底**
      6. 仅当找到有效选项时,才提取选项中字母和点号后面的真实值作为交易对手名称
    * **关键原则**:
      - 用户回复"D" → 查找quote_content中"D.23" → 提取"23"
